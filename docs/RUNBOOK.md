# Эксплуатация

## LiteLLM, 10.10.2026

Текущий маршрут — `INV_LITELLM_URL=https://as.rsmu.ru/litellm`, один `INV_LITELLM_KEY`, `INV_LITELLM_TRUSTED=true`. Alias: `INV_LOCAL_GATEKEEPER_MODEL` и `INV_LOCAL_AUDIO_MODEL` = `local-gemma-4-e4b`, `INV_LOCAL_MODEL=local-gemma-4`, `INV_EMBEDDING_MODEL=local-bge-m3`, `INV_CLOUD_MODEL=gemini-3.5-flash-lite`. Локальный Ollama при таком URL не используется. Не переносить ключ в документацию или frontend.

Дождаться окончания активных задач, остановить воркеры, обновить окружение/образ API, выполнить `python -m app.cli sync-models`, проверить модели и включить облачный deployment через администрирование. Затем запустить CPU/ML/cloud/scheduler с тем же образом. Смена alias сбрасывает health-check и версию маршрута. Не запускать массовые диагностические задания: `/models` не вызывает генерацию, а health-check облачной модели расходует запрос. У текущего провайдера лимит владельца 500 запросов в сутки; полный учёт запросов других приложений остаётся на стороне провайдера/шлюза.

Запросы к шлюзу идут напрямую, без прокси. Текущий host-порт тестового Redis — 16379 вместо занятого Windows 56379. [Отчёт](EPIC_LITELLM.md).

## OCR и LOCAL_CONNECTION, 03.10.2026

Ошибка LOCAL_CONNECTION означает сбой соединения backend с локальной моделью; доступ телефона к сайту при этом может работать. Проверить endpoint из ML-контейнера и процесс Ollama на хосте: контейнер ML сам Ollama не запускает. `GET /api/tags` Ollama и `GET /models` доверенного OpenAI-совместимого сервера проверяют соединение без инференса. Не выводить ключи в журнал. При остановленном Ollama запустить `ollama serve` с `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`.

С 03.10 OCR использует deployment `privacy_asr` и его `endpoint_ref`, то есть ту же локальную визуальную модель, что первичная проверка. В текущей установке это Gemma-4-e4b на доверенном сервере. При отсутствии отдельной первичной модели bootstrap оставляет Ollama; облачного fallback у OCR нет. Миграция БД не нужна. После обновления ML-образа явный повтор OCR получает актуальный маршрут; уже завершённые ошибочные задачи не запускаются автоматически. OCR, ASR и первичная проверка используют общий GPU-slot, страницы идут последовательно.

## Обновление до постоянных неподтверждённых карточек

Собрать новый образ, дождаться окончания текущего inference и остановить API/воркеры. Выполнить `alembic upgrade head` (миграция `c90a51d77e20`, существующие вещи получают `confirmed`), затем `python -m app.cli materialize-pending-items`. Команда переносит старые активные загрузки и ожидающие предложения в каталог без вызова моделей, идемпотентна и не возвращает отменённые задачи. Сохранить резервную копию перед обновлением. Запустить API, CPU, ML, scheduler, cloud и пересобранный web с одним и тем же backend-образом.

Новые defaults: `retry.max_attempts_per_stage=3`, `routing.max_external_calls=3`, `routing.max_total_attempts=12`. Существующая административная ревизия автоматически не переписывается: изменить её через настройки, если нужны новые значения. Уже созданные задачи используют сохранённый snapshot; явный повтор получает текущую конфигурацию и обновляет ту же вещь.

Для первичной проверки через тот же доверенный сервер, что и ASR, задать `INV_LOCAL_GATEKEEPER_MODEL=local-gemma-4-e4b`; используются `INV_LOCAL_AUDIO_URL/KEY/TRUSTED/VERIFIED`. Пустое значение оставляет Ollama. После изменения окружения выполнить `python -m app.cli sync-models`. Первичная проверка и ASR разделяют один GPU-slot; облачный worker и приём задач также оставить с лимитом 1. HTTP proxy не нужен для этой настройки. Исходные промпты проверяются `python -m app.cli verify-prompts`.

Красная карточка остаётся в `/items?review_status=error` и первой в очереди проверки. Повтор через `/tasks/{id}/retry` не создаёт новую карточку; ручное исправление названия и подтверждение убирают ошибку. Оставленная без проверки названная карточка остаётся жёлтой, видна поиску и участвует в напоминаниях о сохранённых сроках. Формы проверки и материалы активной неподтверждённой карточки не истекают по TTL временных черновиков; архив и явное удаление доступны обычным порядком.

Начиная с 01.10 nginx обновляет адрес API через Docker DNS каждые 5 секунд. Старый web-образ запоминал IP до перезапуска и мог постоянно возвращать 502 после пересоздания API. При обновлении этой версии обязательно пересобрать web; дальнейшее пересоздание API не требует рестарта nginx. Проверять `/health/ready` через web и загрузку авторизованного каталога, а не только состояние running контейнеров. Во время самого рестарта API кратковременная недоступность возможна.

## Первая установка

1. Скопировать `.env.example` в `.env.local`, задать независимые случайные `POSTGRES_PASSWORD`, `MINIO_PASSWORD`, `INV_JWT_SECRET` (не меньше 32 символов), Origin и HTTPS cookie policy. Файл не публикуется.
2. `docker compose --env-file .env.local build api web`.
3. `docker compose --env-file .env.local up -d postgres redis qdrant minio`.
4. `docker compose --env-file .env.local run --rm api alembic upgrade head`.
5. `docker compose --env-file .env.local run --rm api python -m app.cli bootstrap --login owner --storage`.
6. `docker compose --env-file .env.local up -d --force-recreate api cpu ml scheduler web`.
7. Проверить `/health/ready`, войти через web, создать место и ручную карточку, подтвердить форму. Проверить наличие операции в журнале.

На Linux обеспечить доступ контейнеров к доверенному inference endpoint. Ollama по умолчанию указан через `host.docker.internal`; не открывать его в Интернет. Данные PostgreSQL/MinIO и резервные копии находятся в отдельных Docker volumes. `down` сохраняет volumes; `down -v` удаляет данные и не применяется при обновлении.

Compose не публикует PostgreSQL, Redis, Qdrant и MinIO. Бакет создаётся приватным через bootstrap. API проверяет workspace для каждой загрузки/выдачи медиа. Ссылки не раскрывают S3 object keys. Web nginx проксирует `/api/v1/` и `/health/`.

## Локальный профиль на этом компьютере

Отдельный `deploy/compose.test.yml`: PostgreSQL 55432, Redis 56379, Qdrant 56333, MinIO 59000, только `127.0.0.1`. В нём нет привязки к старым `data/postgres_data` или `data/minio_data` и не предусмотрены постоянные named volumes. `stop` сохраняет контейнеры и их данные; после `down`/пересоздания сохранность тестовых данных и повторное подключение анонимных volumes не гарантируются. Не используйте этот профиль для личного архива.

`.env.local` содержит локальные настройки и предоставленный владельцем ключ доверенного LiteLLM. Старый `.env` не перезаписан. Конфигурация читает `.env`, затем `.env.local`, затем переменные процесса. В контейнерном профиле адреса зависимостей переопределяются внутренними именами сервисов.

При лимите API 192 MiB не запускайте дополнительный Python-интерпретатор через `docker exec` в работающем API: диагностический процесс уже приводил к OOM. Для чтения состояния используйте HTTP admin/health, а для необходимых read-only SQL-запросов — `psql` в PostgreSQL с фактическим именем БД из конфигурации. Подробности — [проверка личных кейсов](EPIC_REAL_CASE_QA.md).

## Модели и граница доверия

`gemma3:4b` через Ollama — text/image, ровно один image input. `bge-m3:latest` — 1024 измерения. `local-gemma-4-e4b` на `https://as.rsmu.ru/litellm` признан владельцем доверенным сервером и проверен с `input_audio` WAV. Ключ находится только в `.env.local`. Обработка аудио и коллажа выполняется последовательно. Поддержка одновременного audio+image не заявляется.

```powershell
uv run python -m app.cli model-health
uv run python -m scripts.probe_audio --url https://as.rsmu.ru/litellm --model local-gemma-4-e4b --key-env-file .env.local
```

Пример с тишиной не отправляет личные данные. Для проверки разрешённой записи добавить `--wav tests/cases/case_1/audio.wav`. После успешной проверки доверенного endpoint устанавливаются `INV_LOCAL_AUDIO_TRUSTED=true`, `INV_LOCAL_AUDIO_VERIFIED=true`, URL/model/key. После изменения развёртывания повторить проверку. Если bootstrap выполнен до настройки аудио, зарегистрировать deployment через повторяемую команду `sync-models` и проверить его через административный API.

Настройки `INV_CLOUD_*` относятся к внешнему AI. Они независимы от доверенного аудио endpoint. Cloud выключен по умолчанию. Его включение не разрешает отправку local-only карточек, партий, мест или медиа. Неизвестная чувствительность запрещает cloud. Реальные внешние провайдеры в этой приёмке не использовались; HTTP-контракты и ошибки проверены локально. Инференс никогда не получает SQL или полномочий записывать учёт.

## Обновление и миграция

Сначала создать резервную копию. Остановить API/воркеры, обновить код/образ, выполнить Alembic, затем запустить процессы. `alembic check` подтверждает совпадение схемы с моделями. SQLAlchemy `create_all` используется только в SQLite тестах.

После замены API пересоздать также nginx: `docker compose --env-file .env.local up -d --force-recreate api cpu ml scheduler web`. Иначе работающий nginx может продолжать обращаться к прежнему внутреннему IP контейнера. Это проверено отдельным повторным контейнерным smoke.

Старая схема `public` сохранена. Для переноса карточек выполнить `python -m app.cli legacy-preview --workspace-id UUID`, затем проверить предложения. Старые распознанные данные не объявляются автоматически подтверждёнными.

Все шесть исходных промптов проверяет `python -m app.cli verify-prompts`. Изменение промптов не подменяет snapshot ожидающей задачи: старая задача получает безопасную ручную форму, повтор создаётся явно с новой ревизией.

## Очередь и зависимые сервисы

`/health/live` проверяет только HTTP-процесс. `/health/ready` проверяет PostgreSQL, Redis и heartbeat трёх обязательных процессов: scheduler, CPU и ML. При отсутствии воркера возвращается 503 `degraded`; поля `saving_available` и `recognition_available` показывают, какая функция недоступна. Heartbeat обновляется каждые 10 секунд и истекает через 11 секунд. Проверка не запускает inference. Тот же статус доступен вошедшему пользователю через `GET /api/v1/processing-status`.

Статус также возвращает `gpu_state` и `queues_paused`: карантин или пауза default отключают доступность распознавания; пауза CPU — сохранения. Во время карантина новая AI-задача получает 409 `GPU_QUARANTINED`, ручные команды продолжают работать. Ошибки ConnectError/ConnectTimeout/PoolTimeout означают сбой до отправки HTTP-запроса и не создают карантин. Обрыв записи/чтения ответа и RemoteProtocolError остаются неоднозначными. В диагностике попытки сохраняется `cause_type` без текста запроса и секретов. Уже существовавший карантин нельзя снимать по новой классификации задним числом, если тип прежней ошибки неизвестен.

Если ручные вещи/места остаются «Сохраняем», а файлы — «Файлы проверены», сначала выполнить `docker compose ps -a` и посмотреть логи scheduler/CPU. Ручные команды не используют LLM, но требуют живых scheduler и CPU. У всех контейнеров приложения должна быть политика `restart: unless-stopped`, включая локальные compose-дополнения. После аварийного завершения Docker поднимает процесс; явно остановленный оператором контейнер требует `docker compose start scheduler` (или соответствующий сервис). Не очищать очередь или PostgreSQL ради устранения зависания: scheduler восстановит принятые операции. При обновлении проверять `docker inspect --format '{{.HostConfig.RestartPolicy.Name}}' ИМЯ_КОНТЕЙНЕРА`.

- После потери Redis scheduler перечитает PostgreSQL и заново отправит accepted/queued задачи, подтверждения и outbox. Удалять задачи PostgreSQL нельзя.
- Принятое подтверждение повторяется через `/confirmations/{id}/retry`: сохраняются confirmation/operation IDs, ML не повторяется.
- Ошибка Qdrant не откатывает учёт. Outbox повторяется с задержкой; dead letters и отставание видны в `/admin/metrics`. Поиск возвращает текстовые совпадения с предупреждением при недоступном GPU/индексе.
- После неизвестного таймаута GPU slot остаётся `quarantined`. Убедиться, что физическое выполнение на inference сервере остановлено. Затем `/admin/gpu/recover` с текущим fencing token, `physical_inference_stopped:true` и причиной. Истечение lease не доказывает остановку модели.
- Пауза очереди запрещает новый dispatch; уже начатые вызовы завершаются с fencing-проверкой.
- Диагностический replay и его потомки не могут применяться к учёту. Логи содержат request ID, код ошибки и длительность, без ключей, фотографий и сырого текста.

### Слабый inference: один запрос и отмена накопленных задач

`queue.max_pending_total=1` по умолчанию ограничивает число AI-задач в `accepted/preparing/queued/running/retry_wait` на всё развёртывание. Лимит проверяется в PostgreSQL, включая запросы из разных вкладок и рабочих областей. `queue.max_pending_per_user` для новых установок также равен 1; уже сохранённые значения реестра не переписываются. Отдельный GPU slot по-прежнему обеспечивает единственное выполняемое вычисление. Ручное сохранение фотографий не занимает AI-очередь.

Тестировать реальные модели только последовательно, дожидаясь завершения предыдущего запроса. Не запускать параллельно smoke, model-health и пользовательское распознавание. 429 `ADMISSION_LIMIT` требует ожидания/отмены текущей задачи, а не частого автоматического повтора.

Для окончательной остановки накопленной обработки:

1. Остановить ML/CPU/scheduler соответствующего compose-проекта и поставить очереди `default`, `bulk`, `cloud`, `maintenance`, `cpu` на паузу через admin API.
2. Перечислить задачи всех затронутых рабочих областей и отменить каждую с `can_cancel=true` через `POST /tasks/{id}/cancel`. Дождаться сохранения `cancelled`. Уже применённый учёт это действие не отменяет.
3. Проверить отсутствие незавершённых задач. Простая очистка Redis не заменяет отмену: scheduler восстановит задания из PostgreSQL. Не применять FLUSHALL и не удалять историю БД.
4. Для ручной работы разрешить `cpu` и запустить CPU/scheduler; AI-очереди и maintenance оставить на паузе. Уже отправленные задания outbox проверяют паузу maintenance перед началом индексирования.

После первого этапа [EPIC_SIMPLE_UX](EPIC_SIMPLE_UX.md) проверочный стек `inventory-refactor-test` оставлялся с остановленным ML и карантином GPU: 24 задачи отменены, 7 завершены. Позднее 24.09 владелец запросил очистку данных и подтвердил освобождение inference: предметные данные/задачи/медиа очищены, карантин снят, ML/default/bulk/cpu/maintenance включены, admission=1. Вход и настройки сохранены, Cloud-профиль не включён. Числа и пауза первого этапа — историческое состояние, не инструкция возобновлять старые задачи.

Для возобновления сначала убедиться на inference-сервере, что прежнее физическое выполнение прекращено. Снять карантин через `/admin/gpu/recover` с **актуальным** fencing token и `physical_inference_stopped:true`. Затем запустить ML, разрешить нужную очередь, проверить ровно одну новую задачу. Maintenance возвращать отдельно после этой проверки. Старые отменённые задачи не возобновлять. `/health/ready=200` само по себе не подтверждает готовность или освобождение удалённой модели.

Переиндексация: `POST /api/v1/admin/search/reindex` с авторизацией, workspace и Idempotency-Key. Создаётся теневая коллекция, сравниваются текущие версии PostgreSQL, затем alias переключается атомарно. Все workspace пересобираются вместе, фильтрация по workspace сохраняется. Старую коллекцию можно удалить отдельно после проверки; она не источник истины.

## Настройки

API возвращает желаемую и эффективную ревизии; полный будущий UI обязан показывать их раздельно. Изменения concurrency/hard timeout применяются после перезапуска CPU/ML/scheduler. Подтверждение запуска от всех этих компонентов переводит ревизию в effective. Экстренный запрет внешней передачи действует сразу. Rollback создаёт новую ревизию, не стирая историю. Покрытие текущего UI ограничено [EPIC_FRONTEND.md](EPIC_FRONTEND.md) и T-57 в [ACCEPTANCE.md](ACCEPTANCE.md).

Снижение срока хранения сначала проходит dry-run и подтверждение последствий. Автоудаление архива по умолчанию выключено. Отсрочка физического удаления по умолчанию 30 дней. До начала hard purge можно отменить задание. Операционные исправления не создают отдельного обучающего набора при `datasets.enabled=false`.

## Backup и restore

```sh
python -m app.cli backup --output /app/data/backups/2026-09-17
python -m app.cli deletion-ledger --output /app/data/backups/current-deletions.json
```

Копия включает согласованный `pg_dump` снимок схемы `inventory`, manifest/контрольные суммы и приватные медиа. Экспорт пользователя JSON/CSV/ZIP не заменяет backup. Секреты развёртывания резервируются владельцем отдельно. Расписание запуска backup и выгрузку копий на другой диск настраивать на хосте; пример команды выше предназначен для ежедневного cron/Task Scheduler. Регулярно обновлять отдельный `current-deletions.json`, особенно после удаления, и хранить рядом с копиями вне основного диска.

Восстановление выполняется в отдельную пустую БД и выделенное хранилище, при остановленном приложении:

```sh
python -m app.cli restore --input /app/data/backups/2026-09-17 --deletion-ledger /app/data/backups/current-deletions.json
alembic upgrade head
```

Перед записью проверяются пути и контрольные суммы. Старый снимок дополняется актуальным журналом удалений: удалённые после копии объекты повторно очищаются до выдачи клиентам. Сессии и временные экспорты отзываются. Затем восстановить Qdrant из PostgreSQL. Пробный backup/restore на двух временных PostgreSQL БД проверен автоматическим тестом.

Сброс пароля владельца: `python -m app.cli reset-password --login owner`. Пароль вводится без эха; действовавшие сессии отзываются.

## Локальная проверка с Android по Wi-Fi

27.09.2026 для текущего verify-стека включён адрес `http://192.168.31.111:18080`. С 10.10.2026 в игнорируемом `deploy/compose.verify.yml` web публикует порт 80 только на `127.0.0.1:18080`, а Windows portproxy перенаправляет с Wi-Fi-адреса `192.168.31.111:18080` на этот локальный порт. Причина изменения: при пересоздании web Docker преобразовал дополнительные IP-привязки в loopback с пустыми номерами портов и не смог запустить контейнер из-за конфликта порта. HTTP Origin добавлен в `INV_CORS_ORIGINS`; `INV_COOKIE_SECURE=false` сохранён для локальной проверки. API, Redis, PostgreSQL, Qdrant и MinIO доступны на хосте только через loopback.

В Windows создано правило `Inventory-WiFi-18080`: входящий TCP 18080, локальный адрес `192.168.31.111`, источник `192.168.31.0/24`. Ограничение по имени интерфейса снято при диагностике 10.10; ограничения адресов и порта сохранены. Правило действует для всех профилей, потому что текущая сеть помечена Public; категория сети и общие правила брандмауэра не изменялись.

Для входа, ручных операций и загрузки готовых файлов достаточно открыть `http://192.168.31.111:18080` в Chrome на Android. Исправление от 27.09 устраняет зависимость этих действий от `crypto.randomUUID`: используется UUID v4 из `crypto.getRandomValues`, доступного на локальном HTTP. После обновления web перезагрузить страницу на телефоне.

Для записи микрофона непосредственно в браузере по HTTP нужен отдельный временный режим: открыть `chrome://flags/#unsafely-treat-insecure-origin-as-secure`, указать ровно `http://192.168.31.111:18080`, выбрать Enabled и перезапустить Chrome. Исключение не шифрует HTTP. После теста вернуть флаг в Default; для постоянного доступа настроить HTTPS с сертификатом, которому доверяет телефон. Загрузка готового аудиофайла работает без исключения. [Пояснение Chromium](https://www.chromium.org/Home/chromium-security/deprecating-powerful-features-on-insecure-origins/).

Перезапуск текущего развёртывания после изменения адреса или Origin:

```powershell
docker compose -p inventory-refactor-test -f deploy/compose.test.yml -f deploy/compose.verify.yml --profile cloud up -d --no-deps api
docker compose -p inventory-refactor-test -f deploy/compose.test.yml -f deploy/compose.verify.yml --profile cloud up -d --no-deps --force-recreate web
```

При смене IP ноутбука обновить адрес Windows portproxy, Origin, адресное ограничение правила Windows и исключение Chrome; текущий адрес показывает `ipconfig`. Для отключения Wi-Fi-доступа удалить LAN Origin и пересоздать API, затем из PowerShell администратора выполнить `netsh interface portproxy delete v4tov4 listenaddress=192.168.31.111 listenport=18080` и `Remove-NetFirewallRule -Name Inventory-WiFi-18080`.

### Временная точка Inventory-Test, 10.10.2026

Для проверки телефона в обход домашнего роутера с согласия владельца запущена защищённая точка Windows `Inventory-Test`: WPA2, 2,4 ГГц, адрес ноутбука `192.168.137.1/24`. Пароль сгенерирован отдельно и не включён в документацию или Git. Использована конфигурация только текущего сеанса WinRT `StartTetheringAsync(sessionConfiguration)`; сохранённые имя и пароль системной точки доступа не менялись. После выключения или перезапуска Windows этот тестовый сеанс нужно запускать заново. [Описание Microsoft](https://learn.microsoft.com/en-us/uwp/api/windows.networking.networkoperators.networkoperatortetheringsessionaccesspointconfiguration?view=winrt-26100).

Телефон подключается к `Inventory-Test` и открывает `http://192.168.137.1:18080/login`. Windows portproxy перенаправляет TCP с `192.168.137.1:18080` на `127.0.0.1:18080`; правило `Inventory-Hotspot-18080` разрешает вход только на этот адрес и порт из `192.168.137.0/24`. Точный Origin добавлен в verify overlay. На ноутбуке проверены HTTP 200 страницы входа и readiness через localhost, домашний Wi-Fi IP и IP точки; CORS preflight для точки возвращает её Origin и разрешение credentials. Все десять контейнеров запущены. Проверка доступа с физического телефона требует отдельного подтверждения владельца. Модели при сетевой диагностике не вызываются.

Прежний таймаут телефона через домашний Wi-Fi не объяснён окончательно: во время подтверждённых попыток в захвате на ноутбуке не было входящих пакетов телефона. Доступность роутера с телефона сама по себе не подтверждает связность телефона с ноутбуком. Настройки роутера и VPN не менялись.

При проверке точки `Inventory-Test` телефон Pixel 9 Pro подключился и получил `192.168.137.145`; владелец сообщил о таймауте сайта. Во время повторной подтверждённой попытки Packet Monitor получил служебный UDP-трафик телефона и ICMP, но ни одного TCP-пакета к порту 18080. Один из двух ICMP-запросов ноутбука получил ответ телефона. После включения режима полёта с отдельно включённым Wi-Fi владелец подтвердил открытие сайта через точку; web access log содержит HTTP 200 страницы и ресурсов Android Chrome. Ответ 401 на refresh без сессии ожидаем и не означает сетевую ошибку. Это подтверждает доступ через точку в данном режиме, но не определяет окончательно причину выбора маршрута телефоном. Обычный доступ через домашний Wi-Fi с мобильной передачей данных ещё проверяется. Захват ограничен 54 байтами пакета, остановлен; временные фильтры удалены, материалы остаются в игнорируемой `.cache/`.

При повторной проверке 10.10 точка оказалась выключена, а таймер отсутствия клиентов включён. Точка повторно запущена с прежним паролем; таймер отключён на время ручного теста. Проверены состояние `On`, работа виртуального адаптера, `IsNoConnectionsTimeoutEnabled=false` и HTTP 200 страницы входа. До изменения таймер был включён; после теста его нужно вернуть. Это отдельная системная настройка, а не часть временной конфигурации SSID. По [документации Microsoft](https://learn.microsoft.com/en-us/uwp/api/windows.networking.networkoperators.networkoperatortetheringmanager?view=winrt-26100), включённый таймер выключает точку через пять минут без клиентов; факт срабатывания именно таймера в данном случае отдельно не подтверждён.

После теста точку можно выключить в Windows: «Параметры → Сеть и Интернет → Мобильный хот-спот». Для удаления её публикации и восстановления таймера выполнить в PowerShell администратора:

```powershell
netsh interface portproxy delete v4tov4 listenaddress=192.168.137.1 listenport=18080
Remove-NetFirewallRule -Name Inventory-Hotspot-18080
Add-Type -AssemblyName System.Runtime.WindowsRuntime
$null = [Windows.Networking.NetworkOperators.NetworkOperatorTetheringManager,Windows,ContentType=WindowsRuntime]
[Windows.Networking.NetworkOperators.NetworkOperatorTetheringManager]::EnableNoConnectionsTimeout()
```

Удалить `http://192.168.137.1:18080` из `INV_CORS_ORIGINS` verify overlay и пересоздать API. Локальный доступ и отдельные правила домашнего Wi-Fi сохраняются. HTTP-ограничение записи микрофона относится и к адресу точки доступа; загрузка готовых файлов его не требует.

Первичная проверка с ноутбука: HTTP 200 сайта и readiness по LAN IP, вход и восстановление сессии в отдельном Chrome с тестовым исключением и экраном 393×851, доступность облачного выбора, отсутствие горизонтального переполнения в каталоге и форме загрузки.
