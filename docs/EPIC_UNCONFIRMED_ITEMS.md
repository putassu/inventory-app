# Новые вещи до ручной проверки

Реализация и проверка: 30.09–01.10.2026. Уточнение владельца: автоматически сохраняются только **новые вещи**. Пополнение существующей карточки, расход, перемещение и объединение выполняются после подтверждения. Это изменение заменяет исходное требование AGENT.md об отсутствии любого предметного учёта до HITL. Настроенные промпты сохранены без изменений.

## Поведение

Принятая задача добавления сразу создаёт реальную вещь, исходный остаток присутствия и связи с материалами. До получения названия используется «Вещь без названия». Каталог, содержимое места и поиск читают эту же запись; отдельная временная карточка не дублируется. После подготовки фото появляются нормализованные варианты и миниатюры. Фактические сведения модели заменяют предварительные данные в той же карточке.

| review_status | Представление | Значение |
|---|---|---|
| processing | Синий, «Распознаётся» | Задача принята и обрабатывается |
| unconfirmed | Жёлтый, «Не подтверждено» | Название есть; ручная проверка не обязательна для использования |
| error | Красный, «Ошибка распознавания» | Не удалось получить название либо обработка окончилась ошибкой |
| confirmed | Зелёный, «Подтверждено» | Пользователь сохранил ручную форму или подтвердил сведения |

Цвет дублируется текстом, архив обозначается отдельно. «Проверить позже» оставляет вещь жёлтой. Сохранённые сроки участвуют в обычных напоминаниях без фильтра по подтверждению; уведомление содержит отметку о непроверенной карточке. Если срок неизвестен, приложение не придумывает дату. Неподдерживаемый таймер может блокировать подтверждение соответствующей части запроса, но не скрывает уже сохранённую новую вещь.

Команда `verify_item` подтверждает или исправляет уже созданную вещь: идентификатор сохраняется, количество заменяется, а не суммируется. Повтор receipt не добавляет вещь и остаток ещё раз. Ручные изменения, сделанные во время работы модели, сохраняются; поздний результат предлагается для сравнения в форме с предупреждением. При изменившейся структуре остатков проверка может потребовать отдельно разрешить конфликт — автоматического перезаписывания такого учёта нет.

Если запрос оказался поиском или изменением существующей вещи, предварительная карточка архивируется. OCR и административный диагностический replay не создают предметный учёт. Автосохранение фиксирует происхождение через Task и Evidence без фиктивной подтверждённой операции пользователя. Существующие операции и их история не переписываются.

## Ошибки и повторы

Defaults: `retry.max_attempts_per_stage=3`, `routing.max_external_calls=3`, `routing.max_total_attempts=12`. Три попытки включают первую. Повторяются некорректный JSON, отсутствие названия, неизвестный кандидат, превышение выходного лимита и временные ошибки модели. Повторы последовательные, с backoff; задача учитывает общий бюджет вызовов и deadline. Недопустимые файлы, запреты политики, ошибки ключа или неопределённое завершение прежнего физического inference могут завершить обработку раньше.

После исчерпания попыток материалы и красная карточка остаются доступны для ручного исправления. Ошибки идут первыми в очереди проверки. Явный `/tasks/{id}/retry` использует прежние `catalog_item_ids`, закрывает старую форму и создаёт новую обработку с текущими настройками. Сохраняется защита от повторного запуска устаревшей задачи и от изменения уже подтверждённой карточки. Успешное ручное подтверждение снимает ошибку задачи.

Уже записанная административная ревизия не заменяется новыми defaults автоматически. В проверочном развёртывании значения обновлены явно; старые задачи сохраняют свои snapshots. Локальный слот, облачный worker и admission в этом окружении ограничены единицей. Облако включено, HTTP-прокси не задан.

## API и интерфейс

DTO каталога, поиска и деталей включает `review_status`, `review_task_id`, `review_proposal_id`, `recognition_error`; DTO задачи — `catalog_item_ids`, `attempt_count`, `max_attempts_per_stage`, `can_retry`. Клиент использует `can_retry`, а не самостоятельно выводит возможность повтора из текста ошибки. Фото имеют прежний авторизованный контракт `photos[]`.

`GET /items` и `GET /search` принимают `review_status` и `sort`:

| sort | Порядок |
|---|---|
| newest / oldest | По дате создания |
| name_asc / name_desc | По названию |
| status | error → unconfirmed → processing → confirmed |
| expiry | Ближайший известный срок, неизвестные в конце |
| relevance | Только поиск: по релевантности |

Пагинация использует составной ключ с ID и привязку cursor к фильтрам. При смене условий клиент сбрасывает cursor, сохраняя выбранные чекбоксами вещи в верхнем блоке. Окончание очередного этапа обновляет каталог, открытую карточку и содержимое места. Кольцо равных стадий и превью остаются в задачах. Состояние задачи и статус проверки вещи не взаимозаменяемы.

## Проверки и их границы

Локальные проверки покрывают создание до распознавания, поиск и напоминание для неподтверждённой вещи, неизвестное имя, красный приоритет, повторы без дублей, подтверждение без повторного остатка, обычные изменения существующих вещей, TTL материалов, перенос прежних задач, сортировки/курсоры, доверенный адаптер и ручную правку во время inference. Финальный общий прогон: **274 passed, 6 skipped за 280 секунд**; пропуски — отдельные opt-in проверки PostgreSQL/Redis/backup. Профильный модуль после последней правки: **15 passed**. Frontend: **95 passed**, ESLint и production-build прошли; остаётся предупреждение о размере JS-бандла больше 500 kB. Ruff прошёл; все шесть исходных промптов побайтно совпадают с baseline. Реальная PostgreSQL проверена применением миграции и браузерными операциями; это не повтор всех конкурентных opt-in тестов.
