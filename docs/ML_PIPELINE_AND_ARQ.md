# ML Пайплайн, Очереди и Маршрутизация моделей

Архитектура системы обработки построена вокруг асинхронных воркеров, оркестрации LLM/VLM через LangGraph и строгой прокси-маршрутизации (LiteLLM) для стабильной работы и экономии лимитов.

## 🔀 Управление задачами (ARQ Queues)
Для предотвращения блокировки вычислительных ресурсов GPU, обработка разделена на независимые пулы воркеров (Redis + ARQ). 

### Структура очередей:
1. `high_priority` (Приоритетная очередь): Используется для быстрых ответов и продолжения работы после Human-in-the-Loop (HITL). Задачи из UI (разрешение конфликтов `user_action_required`) обрабатываются здесь без задержек.
2. `default` (Стандартная очередь): Обработка инференса, потоковая загрузка данных от обычных пользователей. Воркеры резервируют 80% времени для этой очереди.
3. `bulk` (Очередь массовой загрузки): Обрабатывает задачи пользователей, массово загружающих сотни фотографий (более 5 активных задач), чтобы не мешать остальным юзерам.
4. `cron_only` (Очередь шедулера): Выделенный воркер исключительно для периодических фоновых задач:
   - Ежедневное обнуление лимитов LiteLLM.
   - Еженедельный Garbage Collector.
   - Ежедневный расчет сроков годности (Expiry Dates) и отправка предупреждений по перцентилям.
   - Ежечасный парсинг крон-джобов и отправка `remind_at` уведомлений.

## 🧠 ML-Пайплайн (LangGraph StateGraph)
Обработка медиа (аудио, текст, фото) управляется графом состояний (StateGraph). Пайплайн реализует *Task Chunking* — способность прерываться и ожидать решения пользователя в HITL.

**Узлы графа и их условия:**
1. `preprocess_and_upload_node`: Загружает исходники из MinIO. Фотографии сжимаются, генерируются миниатюры (thumbnails) и собирается коллаж (до 3 фото по вертикали).
2. `gatekeeper_node`: Первичный фильтр и ASR на базе **local-gemma-4-e4b**. 
   - Выполняет транскрибацию аудио в текст.
   - Проверяет `is_safe` (наличие паспортов, кредиток, лиц). Если `is_safe=False`, система запускает **изолированный цикл фолбэков** (перенаправляет задачу только на локальные модели, минуя облачные, чтобы не слить приватные данные).
   - Извлекает сущности-кандидаты и выполняет **RAG-инъекцию**. Векторный поиск находит похожие вещи в БД и подставляет в промпт для последующих VLM узлов контекст в виде строки: *«В базе пользователя уже есть похожие вещи: {name} (Сходство {score}), возможно это они»*.
3. `cloud_gemma_extract_node`: **Gemma 4:31b (Cloud)**. Запускается, если данные безопасны. Извлекает интенты, локации и структуру JSON на основе фото и гибридного RAG-контекста.
4. `local_gemma_extract_node`: **Gemma 4 (Local)**. Вызывается, если Gatekeeper пометил `is_safe=False` или пользователь включил режим `local_only`. Использует оптимизированный коллаж вместо тяжелых одиночных фотографий для экономии VRAM.
5. `cloud_gemini_extract_node` (Fallback): Резервный вызов **Gemini 3.5 Flash**. Запускается, если у предыдущих моделей `confidence_score` оказался ниже допустимого порога, и данные при этом не помечены как приватные.
6. `extract_schedule_node`: Узел парсинга сложных расписаний. Пытается извлечь дату через Python, при неудаче просит LLM сгенерировать `cron_schedule` или `remind_at` формат.
7. `hitl_node` (Human-in-the-Loop): Узел-прерыватель. Срабатывает при низком `confidence_score`, ошибках парсинга дат, 100% дубликатах в разных локациях, или когда локальная модель не справилась с приватными данными. Ожидает вмешательства пользователя (статус `user_action_required`).
8. `execute_db_writes_node`: Финальный узел записи в Postgres и векторный Qdrant.

## 🛡️ LiteLLM и обход DPI-блокировок
Все обращения к облачным провайдерам (Google Gemini/Gemma, OpenRouter) проходят через единый API-шлюз LiteLLM и Nginx Proxy (`http://10.0.245.10:4000`).

### Проблема блокировок потоковой передачи (DPI)
Ранее наблюдалась проблема, когда системы глубокого анализа трафика (DPI) обрывали долгие соединения, если они использовали потоковую передачу (Streaming/SSE).

### Решение: Форсирование монолитных REST запросов
Поскольку ML-пайплайну для сохранения в БД нужен **полный валидный JSON-ответ**, потоковая генерация (`stream: True`) нам не нужна.
Для прохождения DPI:
1. В настройках LiteLLM выставлен `force_non_streaming: True`.
2. Клиент отправляет стандартный POST запрос с `stream: False`.
3. Соединение ожидает полной генерации. DPI **не блокирует** такие долгие монолитные соединения, в отличие от потоковых, обеспечивая 100% доставку JSON-ответов без промежуточных костылей (отказ от `stream_killer`).

### Квоты и Fallbacks в LiteLLM:
- При исчерпании лимитов (`429 RateLimitError`) ключ отправляется в карантин на сутки (`CooldownTime: 86400`).
- Применяется Waterfall Routing: При падении основной модели, запрос автоматически переключается на следующий в пуле (напр., `gemini-3.5-flash` -> `gemini-3-flash`).
