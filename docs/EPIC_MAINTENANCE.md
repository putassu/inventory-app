# Эпики 4, 8 и 9: хранение, сроки, экспорт и восстановление

Проверено 17.09.2026. Основание: AGENT.md, разделы 14–17, 18.7–18.8 и 20; сценарии T-73, T-74, T-76. Этот отчёт описывает выполненные изменения и пределы проверок.

## Сроки и inbox

Планировщик создаёт уведомления только по срокам еды, лекарств и документов. Дата годности включительна: сообщение «срок истёк» возникает со следующего локального дня. Неизвестное количество сохраняется и помечается «наличие не подтверждено»; израсходованные партии исключаются. Поколения срока и правила позволяют отменять прежние occurrences, а уникальные ключи предотвращают повторную доставку. После простоя из нескольких прошлых порогов выбирается последний актуальный.

Проверяются часовой пояс, формат ЧЧ:ММ, тихие часы и поддерживаемый канал in_app. Несуществующее локальное время при переходе на летнее время переносится вперёд на размер разрыва. Snooze действительно скрывает уведомление до выбранного времени. Область локаций проверяется в workspace пользователя. Сущностей графика приёма лекарств и произвольных таймеров нет.

## Экспорт

JSON/CSV/ZIP собираются из подтверждённого состояния. PostgreSQL использует REPEATABLE READ; файл содержит export.v1, временную зону, версии справочников и ревизию workspace. Медиа сопоставляются с карточками через media и media_bindings. ZIP содержит контрольные суммы файлов. CSV экранирует формулы и управляющие символы в начале ячейки. Auth/session/config/credentials не включаются.

Срок ссылки проверяется при каждом чтении, независимо от работы GC. Удаление карточки отзывает ранее созданные и ещё строящиеся экспорты workspace. Проверена гонка, когда запись файла завершается уже после запроса удаления: доступ остаётся закрытым, GC удаляет байты. История операций с удалёнными данными не попадает в новые экспорты.

## Удаление и период восстановления

Deletion preview фиксирует карточки, версии партий и остатков, связанные задачи и предложения, bindings, общие медиа и объём эксклюзивных файлов. Изменение этой области требует нового preview. Подтверждение с hash/revision немедленно ставит lifecycle=deleted, создаёт tombstone, отменяет связанные незавершённые задачи с новым fencing token и закрывает карточки, формы, историю и медиа для чтения.

Общая фотография остаётся доступной, пока есть другая живая карточка или незавершённая задача. Когда удалена последняя живая ссылка, чтение закрывается немедленно. Физическое удаление проверяет реальные bindings и сохраняет байты, которые ещё нужны другой карточке или периоду восстановления.

До начала hard purge доступна явная отмена:

```http
POST /api/v1/purge-jobs/{id}/cancel
Idempotency-Key: <новый UUID>

{"expected_version":1,"explicit_confirmation":true}
```

Она возвращает карточки в active, открывает их медиа, снимает tombstone и восстанавливает доступную историю операций. Старые AI-задачи и предложения не запускаются повторно. Их исходный ввод, текущие формы и кэшированные ответы очищаются сразу при запросе удаления; отмена удаления восстанавливает каталог и историю подтверждённых операций, а не эти временные материалы. Список заданий для восстановления доступен через `GET /api/v1/purge-jobs` с limit/cursor. После начала физической очистки отмена запрещена.

Hard purge удаляет ссылки и байты отдельными повторяемыми шагами; перед обращением к storage фиксируется manifest и статус purging. После прерывания обработка продолжается с того же manifest. Очищаются атрибуты, серийные номера, описания, даты, остатки, aliases, evidence, JSON истории, receipts, confirmations, все ревизии форм, task diagnostics, уведомления, idempotency responses и сохранённые deletion previews. Остаются технические идентификаторы и минимальный tombstone. Пустой остаток сам по себе никогда не запускает purge.

GC восстанавливает прерванное удаление orphan media и просроченных экспортов, удаляет только объекты вне живых references и запускает заранее разрешённую политику очистки явно архивированных карточек. Ревизия этой политики фиксируется в manifest. Настройка архивной автоочистки по умолчанию выключена.

Загрузка медиа читает файл и обращается к storage вне транзакции записи. Блокировка workspace используется только для заключительной проверки idempotency и сохранения ссылки; неподтверждённые orphan bytes после сетевого/транзакционного сбоя подбирает GC.

## Backup/restore

Backup использует pg_export_snapshot и pg_dump одной схемы inventory. Версия миграции и приложения, object references, контрольные суммы БД/медиа и журнал удалений входят в manifest. Пока копируются медиа, SHARE-блокировка таблицы media_assets не позволяет purge/GC перейти к физическому удалению файлов этого снимка. Это короткое обслуживание без обращения к модели, но загрузки медиа могут ждать завершения копирования.

Restore разрешён только в отдельную БД без схемы inventory. До записи проверяются все пути и контрольные суммы. pg_restore выполняется одной транзакцией с остановкой на ошибке. Старые сессии и временные экспорты отзываются. Журнал из backup объединяется с **актуальным** внешним журналом удалений; затронутые предметы повторно удаляются до завершения восстановления.

Актуальный журнал нужно сохранять отдельно от старого backup командой `python -m app.cli deletion-ledger --output <путь>`. Журнал из старой копии сам по себе не содержит удаления, сделанные после этой копии. Сам backup может содержать прежние данные до истечения политики его хранения; восстановление не делает эти данные доступными, если передан актуальный журнал. PostgreSQL client нужен в образе обслуживания; секрет подключения передаётся через окружение процесса, а не аргументы или сообщения об ошибке.

Пределы проверки: стандартные транзакционные сценарии этих тестов используют SQLite; snapshot и backup/restore отдельно проверены на настоящем PostgreSQL. Отказы объектного хранилища воспроизведены на адаптере с локальными приватными файлами; S3-совместимость проверяется общим прогоном приложения. Push и обучение на датасетах не входят в этот эпик; очистка готовых датасетных копий потребует адаптера, когда появится их запись.

## Финальная проверка настроек хранения

Автоматический GC теперь соблюдает `retention.gc_interval_hours`. В PostgreSQL сохраняются время последнего успешного прохода и lease текущего. Периодический вызов раньше срока пропускается; ручной запуск администратора использует force. Ошибка очищает lease, но не отмечает проход успешным, поэтому восстановление не ждёт следующего суточного интервала.

Один расчёт кандидатов используется и очисткой, и dry-run политики. Impact показывает **дополнительные** карточки, исходный текст/аудио задач, незавершённые формы и файлы, которые затрагиваются новой политикой, их байты и типы, общие количества, ближайший GC и первый новый hard purge. Проверены старый и свежий архив, активная карточка, уже просроченная и вновь затронутая фотография. Сохранение сокращённого срока без `impact_confirmed` возвращает 409 и ничего не удаляет. Уже принятые сроки существующих purge jobs сохраняются: для них показываются ноль изменённых заданий и фактическое число сохранённых grace periods.

`retention.source_photo_days` действует отдельно от TTL текста/аудио. `null` сохраняет фото завершённой задачи с её binding. При заданном сроке неиспользуемый source image удаляется вместе с терминальными task bindings, но фото активной карточки или незавершённой задачи остаётся. Удаление аудио/текста не снимает привязки исходных фотографий автоматически. Срок незавершённых форм применяется также к ручным предложениям.

Опциональные функции датасетов, дополнительного кэша списков и verbose с сохранением payload в этой поставке недоступны. Их поля schema имеют `editable=false` и русское объяснение; изменение фиксированных значений отклоняется как `UNSUPPORTED_SETTING`, а не сохраняется с ложным обещанием эффекта. Обычная диагностика без исходных payload остаётся доступной.

Стартовый общий бюджет ML-вызовов увеличен с 4 до 6: запись до 60 секунд с частями по 20 секунд и перекрытием в одну секунду требует до четырёх ASR-вызовов, затем проверки и извлечения. Параметр по-прежнему изменяется администратором в диапазоне 1–12; меньший бюджет не обходится скрытыми повторами.

Дополнительная приёмка закрыла T-67, T-69 и T-78. Подтверждённый расход последней таблетки отменяет все будущие occurrences, сохраняя depleted-карточку и историю. Два последовательных подтверждения нового срока отменяют оба старых поколения; доставляется только последнее. Удаление исходного WAV и транскрипта по TTL сохраняет количество и неизменную структуру и значения JSON истории подтверждённой карточки. Итоговый полный прогон этих модулей: **48 passed за 19,02 секунды**.

Финально добавлены T-26 и T-68: безымянное фото получает временную карточку только после подтверждения, а документ untracked с quantity=null получает уведомление по сроку. Отдельный API-тест проверяет честный ответ ручного GC: при чужой активной lease возвращается running, после её освобождения — completed. Итоговый повторный прогон обоих модулей: **51 passed за 30,40 секунды**.

Дополнительная проверка T-61 обнаружила привязку cooldown к стартовой конфигурации вместо модели исполняемой попытки. `handle_failure` теперь сохраняет ограничение только для фактического `Attempt.model_id`. В `test_cooldown_v1.py` настоящий CloudAdapter получает HTTP 429 с Retry-After=45 через MockTransport; во время запроса deployment заменяется, а стартовая модель конфигурации отличается от обеих. Проверены сохранённые RATE_LIMIT/reset_at, совпадение next_attempt_at и успешная работа новой модели до истечения ограничения старой. **1 passed за 1,79 секунды**. Внешний сервис этим тестом не вызывается.
