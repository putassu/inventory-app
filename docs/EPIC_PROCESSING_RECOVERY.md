# Восстановление сохранения и распознавания, 26 сентября 2026

## Причина

В действующем локальном стеке scheduler завершился с `redis.exceptions.TimeoutError` и оставался остановленным около 27 часов. У compose-дополнения для этого стека не было `restart: unless-stopped`. API и остальные контейнеры продолжали работать; прежний readiness проверял только PostgreSQL. Два ручных подтверждения остались queued, задача фото/голоса — accepted/upload_verified. Создание мест не обращалось к LLM: не работала доставка заданий CPU.

После запуска scheduler оба подтверждения применились. Личные место, вещь, фото и голос сохранены. Прежняя медиазадача достигла review после ошибки `UNKNOWN_MODEL_CANDIDATE`; она не подтверждалась автоматически.

## Изменения

- Для локальных контейнеров приложения включён автоматический перезапуск после аварийного завершения. В основном docker-compose.yml эта политика уже была. Запущенные хранилища и их volumes не пересоздавались.
- Heartbeat arq сокращён с часового интервала по умолчанию до 10 секунд. Readiness и административная диагностика проверяют scheduler, CPU и ML. Новый авторизованный `/processing-status` разделяет доступность сохранения и распознавания, без inference.
- Интерфейс показывает недоступность соответствующего сервиса. Длительная ручная операция после 10 секунд освобождает форму и продолжает наблюдаться в общем блоке; это не успешное сохранение до applied. Позднее применение обновляет открытый каталог/карточку. Повторы не создают новую операцию; новое намеренное добавление после applied получает новый ключ.
- Отсутствующие после очистки стенда receipt удаляются из локального наблюдения. Ошибка одного receipt не блокирует остальные. Событие applied не рассылается повторно при каждом опросе.
- Для локальной Ollama ответ ограничен JSON Schema: первичная проверка — схемой Gatekeeper, извлечение — существующей LegacyOutput с допустимыми идентификаторами из кандидатов или null. Серверная проверка недоверенных ссылок не ослаблена. Исходные шесть промптов не менялись. Основание формата — [документация Ollama](https://docs.ollama.com/capabilities/structured-outputs).
- Неизвестные атрибуты модели со значением null пропускаются: они больше не вызывают INVALID_ATTRIBUTES для необязательных строковых свойств. На реальном кейсе это были размер, бренд и материал носков. Неверные непустые значения по-прежнему требуют исправления.
- Доступность распознавания учитывает карантин и паузы очередей. При карантине новая AI-задача получает 409 GPU_QUARANTINED до постановки в очередь; повтор прежнего принятого запроса возвращает прежний ID. В форме сохраняется ввод и доступен ручной режим.
- Сетевой отказ до отправки запроса больше не означает неизвестный работающий inference. ConnectError/ConnectTimeout/PoolTimeout не включают карантин; ошибки чтения/записи и протокола сохраняют его. Адаптеры не повторяют запрос автоматически. В попытке записывается только класс исходной ошибки. Основание различения — [исключения HTTPX](https://www.python-httpx.org/exceptions/).

## Проверки

- Заключительный общий backend-прогон: **232 passed, 6 skipped**, 214,97 с. Один из opt-in сценариев отдельно включён и пройден — физическая потеря Redis DB13. Остальные инфраструктурные сценарии PostgreSQL/backup в этом эпике повторно не запускались. Новые проверки покрывают heartbeat, карантин/паузы, admission/replay, JSON Schema, сетевые ошибки и сохранение неизвестных атрибутов без потери количества.
- Frontend после всех исправлений: 79 passed, 16 файлов; ESLint и сборка обоих Docker-образов прошли. Проверка целостности всех шести промптов прошла.
- Chromium: ручное место с фото применилось за 2,27 с, ручная вещь с фото — за 2,91 с; вещь видна внутри выбранного места, миниатюры загрузились. Число вызовов моделей осталось прежним.
- При намеренной остановке scheduler браузер показал недоступность и «Сохраняем: 1», освободил форму через 10,6 с. После запуска место появилось без перезагрузки, в единственном экземпляре.
- При завершении процесса scheduler сигналом TERM Docker сам перезапустил контейнер: RestartCount=1, readiness восстановился до 200. Это проверка аварийного выхода процесса; явно выполненный `docker compose stop` требует последующего start.
- Изолированный инфраструктурный тест физически очистил Redis DB13 при сохранённом PostgreSQL-подтверждении: операция восстановилась и выполнилась один раз, включая позднюю повторную доставку. Рабочая DB14 не очищалась.
- При реальном карантине браузер получил 409 для нового распознавания, сохранил ввод и позволил перейти к ручной форме. Ручная вещь с фотографией применилась за 2,9 с, миниатюра загрузилась. Архивирование трёх тестовых вещей и двух мест прошло без модели; форма архивации проверена при ширине 320 px без переполнения.

Во время проверки обнаружено различие локального Redis-контейнера и нового compose-healthcheck: уже запущенный Redis не имел healthcheck. Локальное дополнение использует service_started для него; основной compose сохраняет service_healthy. Проверка живого Redis на уровне приложения остаётся обязательной. Пересоздание хранилища для этой правки не потребовалось.

На момент ошибки case_9 настройка timeout была 300 с. Прежний адаптер объединял сетевые ошибки под кодом LOCAL_TIMEOUT, поэтому по коду нельзя установить, был ли запрос отправлен. Новая диагностика это различает, но не доказывает состояние прежнего вызова задним числом. Для продолжения запрошено подтверждение физической остановки/завершения на доверенном сервере владельца согласно RUNBOOK. Очередь следующих тестов не создавалась.

Это проверка доставки, состояний, формы и сохранения конкретных материалов, а не сертификат точности Gemma для всех полей. Модель может предлагать неверную категорию, единицу или действие; обязательная человеческая проверка сохранена. Тестовые предложения отменены, три созданные QA-карточки и два QA-места архивированы; пользовательские объекты и исходное предложение не изменялись. Тесты и материалы остаются вне Git.

## Продолжение после ответа владельца, 26.09.2026

Владелец сообщил, что Gemma на доверенном сервере работает и отвечает, и повторно указал ограничение: все модели обслуживают один запрос за раз. При отсутствии активных задач приложения блокировка снята через штатный `/admin/gpu/recover` с актуальным token 119 и записью причины в аудит. Сначала выполнен только повтор case_9; после его завершения последовательно отправлены остальные кейсы. Отменённые задачи не возобновлялись, очередь тестов не накапливалась.

Карантин — состояние блокировки в приложении после неизвестного исхода запроса, а не диагноз сервера модели. Сообщение интерфейса исправлено: оно объясняет приостановку и проверку предыдущего запроса администратором, не требует «восстановить сервер». Новое сообщение проверено в браузере подстановкой только ответа `/processing-status`, без изменения настоящего GPU slot.
