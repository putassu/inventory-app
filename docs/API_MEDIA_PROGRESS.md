# Контракт для будущего клиента

Пути имеют префикс `/api/v1`, требуют access token и `X-Workspace-ID`. URL медиа приватные; клиент загружает их с авторизацией. В списке/деталях карточек и поиске:

```json
{"photos":[{"media_id":"UUID исходника","url":"/api/v1/media/UUID/download","thumbnail":{"media_id":"UUID миниатюры","url":"/api/v1/media/UUID/download","width":256,"height":192}}]}
```

Без фотографий — `photos: []`, без готовой миниатюры — `thumbnail: null`. API не подменяет её большим исходником молча. После удаления карточки применяются правила недоступности файлов.

С 30.09 принятая задача добавления новой вещи возвращает `catalog_item_ids: UUID[]` — реальные карточки каталога, созданные вместе с задачей. Их фото привязаны сразу; подготовленные миниатюры добавляются после CPU-стадии. Одна задача может дать несколько вещей после распознавания, поэтому клиент обновляет список ID при polling. Карточки каталога, поиска и деталей содержат `review_status` (`processing`, `unconfirmed`, `error`, `confirmed`), `review_task_id`, `review_proposal_id`, `recognition_error`. Не создавать поверх них дублирующие временные карточки. Подробнее: [EPIC_UNCONFIRMED_ITEMS.md](EPIC_UNCONFIRMED_ITEMS.md).

С 24.09 такой же `photos[]` возвращается в списке и деталях **мест**. Ручные команды `receive_stock`, `create_location`, `update_location`, а с 01.10 и `update_item` принимают `media_ids: UUID[]`: ID ранее загруженных изображений текущей рабочей области, default `[]`, до 20 ID в одной команде. Клиентская форма ограничивает выбор эффективным `media_limits.max_images` (по умолчанию 3). Сохранение добавляет связи с вещью/местом и создаёт thumbnail до 256 px без LLM. Повтор команды использует существующий механизм Idempotency-Key/receipt. Удаление отдельной связи фотографии этим полем не выполняется; передача пустого списка сохраняет существующие фото.

Фото ручного ввода нормализуется клиентом перед upload, сервер повторно проверяет и декодирует его при создании миниатюры. Непригодное изображение не становится успешно применённой связью. Общие для вещи и места файлы не блокируются при удалении одной из использующих их сущностей.

С 26.09 `GET /processing-status` сообщает heartbeat scheduler/CPU/ML, `saving_available`, `recognition_available`, `gpu_state` и `queues_paused`. Запрос не запускает модели. При карантине новая AI-задача отклоняется с 409 `GPU_QUARANTINED` до создания записи; выбранные файлы можно использовать для ручного ввода. Ручные вещи и места с фото продолжают сохраняться через CPU. Принятое подтверждение, ещё не ставшее `applied`, показывается как продолжающееся сохранение, а не как ошибка распознавания.

`GET /capabilities` возвращает `media_preprocessing`: рекомендации клиенту и жёсткие inference-пределы. Рекомендуемый upload — длинная сторона до 1600 px, JPEG quality около 80; WAV PCM16/16 kHz/mono. Клиент может предложить выбор полезной области фото и обрезку записи пользователем. Автоматическое отсечение речи не должно терять отрицание или начало команды. `POST /media` принимает `client_preprocessed=true`, но сервер всё равно проверяет/нормализует содержимое. Полноразмерный оригинал не обязателен: сжатое фото принимается как исходник.

`width`/`height` исходника при upload описывают закодированные пиксели. EXIF-поворот применяется при подготовке: размеры normalized/thumbnail и manifest соответствуют уже повёрнутому изображению. Upload проверяет контейнер файла; ошибка декодирования обнаруживается CPU worker и видна в задаче, без вызова модели.

С 24.09.2026 capabilities также содержит эффективные изменяемые лимиты приёма из реестра настроек. Пример с defaults:

```json
{"media_limits":{"max_images":3,"max_file_bytes":15728640,"max_task_bytes":47185920,"max_audio_seconds":60}}
```

Клиент читает значения при открытии composer, показывает ограничения и проверяет подготовленные файлы до upload. Длинную запись можно вручную обрезать. Настройки могут измениться до отправки, поэтому сервер остаётся источником истины. Decoded-pixel limit и лимиты polling/batches этим дополнением не публикуются. Inference 512 px и серверный коллаж действуют независимо от транспортных 1600 px. Живой предпросмотр обрезки не является дополнительным исходником для модели.

Пакетный polling: `POST /tasks/status` со списком `{task_id,status_version}`. Отдельный постоянный запрос для каждой карточки не нужен. Ответ задачи:

```json
{
  "stage":"extraction","status":"running",
  "progress":{
    "current":{"stage":"extraction","status":"running","started_at":"2026-09-21T10:00:00+00:00"},
    "history":[{"stage":"media","status":"preparing","started_at":"2026-09-21T09:59:50+00:00","finished_at":"2026-09-21T09:59:52+00:00","duration_ms":2000,"error_code":null}],
    "percent":null,"estimated_remaining_ms":null
  },
  "timing":{"processing_seconds":"2.000000","stage_started_at":"2026-09-21T10:00:00+00:00","server_time":"2026-09-21T10:00:07+00:00"}
}
```

История ограничена 64 переходами. `processing_seconds` — время модельных попыток; подготовка/ожидание видны отдельно в history. Null не означает нулевой прогресс. При 304/unchanged клиент продолжает elapsed-таймер последней стадии. Административная диагностика: `GET /admin/tasks/{id}/trace`.

С 26.09.2026 web показывает стадии в списке и деталях задач равными цветными секциями кольца. Размер секций не зависит от длительности; число в центре — завершённые этапы / число этапов, а не ETA. История и текущий stage определяют состояния, ошибки и пропуски не считаются успехом. Этап голоса присутствует только при аудио, manual не включает модельные стадии; подтверждение человеком отделено от сохранения. В карточке задачи также отображается авторизованное превью `preview_media_id`. API и тайминги для этого не изменялись.

Поступление пары: `quantity:"1",unit_code:"pair"`; одной штуки: `quantity:"1",unit_code:"pcs"`. Новая карточка пары хранит pcs. Для носков с `attributes.counting_unit:"pair"` детали дополнительно содержат `quantity_display:{unit_code:"pair",complete_pairs:1,single_pieces:"1.000000",has_unknown_quantity:false}` при трёх известных штуках. Неизвестное количество — отдельное состояние. Группировка по парам не утверждает совместимость разных цветов/размеров.


## Дополнение 23–24 сентября: текущий web и task DTO

Рефакторинг текущего React-клиента описан в [отчёте frontend](EPIC_FRONTEND_REFACTOR.md). Клиент подготавливает JPEG до 1600 px и WAV PCM16 mono 16 kHz. Это транспортные файлы: backend по-прежнему независимо проверяет медиа и формирует один ограниченный коллаж для модели. Миниатюры скачиваются с авторизацией; отсутствие thumbnail не запускает фоновую загрузку оригинала.

К ответу `task_view` добавлены `input_mode`, nullable `parent_task_id` и `title`. Title содержит первые 160 символов пользовательского текста после нормализации пробелов либо русское название типа ввода. Состояния и `progress/timing` не изменены. Доступ остаётся ограничен рабочей областью. GET архивированного места теперь отвечает 404 `NOT_FOUND` вместо JSON null.

После упрощения UX task DTO также содержит `context: {item_id, location_id}`, nullable `preview_media_id` и `diagnostics_only`. Preview сначала ссылается на первый исходник, после CPU-подготовки — на первую миниатюру. Клиент использует его только с авторизацией. Для обычной карточки вещи/места отсутствие thumbnail по-прежнему не является разрешением автоматически скачать оригинал.

Capabilities дополнен `max_pending_ai_tasks` (default 1) и `ai_processing_paused`. Принятые задачи сразу видны карточками обработки в каталоге/месте, но не входят в подтверждённый остаток. Диагностические задачи исключаются из этих карточек. Статусы имеют текст и цвет; отменённые карточки скрываются. При 429 `ADMISSION_LIMIT` клиент сохраняет форму, предлагает дождаться текущей обработки или заполнить вручную и не создаёт цикл автоматических отправок.

## OCR и выбор модели

С 03.10 OCR выбирает локальный deployment `privacy_asr` и его `endpoint_ref`; в текущем окружении это доверенная Gemma-4-e4b. Кнопка OCR извлекает полный текст для поиска. В форме добавления фото без названия запускает обычную задачу inventory/photo, а не OCR; после 202 показывается созданная карточка обработки. [Проверка и эксплуатация](EPIC_OCR_PHOTO_CREATE.md).

`POST /tasks` с `purpose=ocr,input_mode=photo` последовательно распознаёт фотографии и возвращает `result.ocr_text`, не изменяя учёт. Каждая страница ограничена текущими лимитами runtime (512 px и 256 KiB); для OCR несколько страниц не объединяются в коллаж. Успешные страницы сохраняются в `ocr_parts`, даже при следующей ошибке. Кольцо содержит равные секции приёма, подготовки и OCR; стадии upload_verified → media → ocr → ocr_ready. Текст проверяется в ручной форме и сохраняется как Item.ocr_text. Миниатюры остаются обычными фотографиями карточки.

Для распознавания вещи доступны `privacy.model_preference=local|cloud|default` и `force_local`. Выбор облака не обходит политику приватности. Изменение выбора модели использует отдельный ключ загрузки: уже загруженный local_only файл не повышает разрешения. OCR всегда локален. Подробности — [EPIC_MERGE_OCR.md](EPIC_MERGE_OCR.md).
