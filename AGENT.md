# «Инвентаризатор»: подробное техническое задание и руководство по реализации бэкенда

Версия: 1.0. Дата: 17 сентября 2026 года. Язык интерфейсных сообщений: русский. Формат API: JSON, UTF-8, REST / HTTPS.

Документ предназначен для разработчика бэкенда и содержит продуктовые правила, модель данных, контракты API, алгоритмы обработки, требования к отказоустойчивости, административному интерфейсу и порядок реализации. Это самостоятельная спецификация, заменяющая противоречащие ей технические положения исходного BRD/PRD.

Навигация: [модель данных](#4-подробная-модель-данных) · [HITL и формы](#7-главный-контракт-hitl-предзаполненная-форма) · [коллажи](#9-коллаж-для-локальной-gemma) · [настройки администратора](#16-настройки-пользователя-и-администратора) · [REST API](#18-полный-rest-api-первой-версии) · [порядок реализации](#24-порядок-реализации) · [приёмочные сценарии](#25-проверочные-сценарии).

Обозначения: MUST / «обязательно» — условие корректности; SHOULD / «следует» — рекомендуемая реализация; MAY / «можно» — расширение. Числа в профиле настройки являются стартовыми значениями для экспериментов, если явно не названы инвариантами.

## 0. Решения заказчика и границы документа

### 0.1. Подтверждённые решения

| Код | Решение |
|---|---|
| D-01 | Первый пользователь — владелец приложения. Первая инсталляция рассчитана на личное использование. |
| D-02 | Сервер принадлежит владельцу и является доверенным контуром. Чувствительные данные разрешено передавать этому серверу. Для будущих пользователей предусматривается фиксация принятия соглашения. |
| D-03 | Внешние AI-провайдеры находятся за границей доверенного контура. Согласие на передачу владельцу сервера само по себе не разрешает отправку внешним AI-провайдерам. |
| D-04 | Любое изменение предметного учёта, предложенное AI, требует явного Human-in-the-Loop, далее HITL. |
| D-05 | HITL — удобная предзаполненная форма: обычно одно подтверждение; исправления преимущественно выбором, переключателями, счётчиками и датами. Свободный текст, новая диктовка и повторная съёмка — запасные способы. |
| D-06 | Пользователь допускает медленную локальную обработку и последовательную обработку очереди. Поддерживается сценарий «загрузить много, вернуться и подтвердить результаты». |
| D-07 | Текущий локальный runtime Gemma принимает ровно одно изображение на вызов. Несколько исходных фото необходимо объединять в один коллаж. Это ограничение конкретного развёртывания. |
| D-08 | GigaAM исключена. Аудио обрабатывается локальной Gemma с подтверждённой поддержкой аудио в выбранном runtime. |
| D-09 | Напоминания о приёме лекарств, дозировании и соблюдении графика исключены. Есть напоминания об истекающих и истёкших сроках продуктов, документов и лекарств. |
| D-10 | Оптимизация хранения, кластеризация ради перестановки вещей и рекомендации по заполнению мебели отложены. |
| D-11 | В личном кабинете есть пользовательские настройки и доступный администратору раздел лимитов, таймаутов, моделей, очередей, хранения и диагностики. |
| D-12 | Проценты локальных распознаваний, confidence-пороги, таймауты и лимиты — настраиваемые параметры для последующей калибровки. |
| D-13 | WebSockets запрещены сетевыми условиями. Обновление задач выполняется polling по HTTP. |

### 0.2. Принятые проектные решения

Следующие решения выбраны для согласованной первой реализации. Их можно заменить через архитектурное решение с сохранением внешних контрактов:

- Модульный монолит FastAPI с отдельными процессами воркеров.
- PostgreSQL — источник истины; Redis — очередь, координация и необязательный кэш; Qdrant — восстанавливаемый поисковый индекс.
- PostgreSQL хранит задания, предложения HITL, подтверждения, параметры и историю операций.
- arq — единый механизм выполнения фоновых задач; альтернативные Celery и встроенный планировщик FastAPI не используются.
- S3-совместимое хранилище MinIO находится в доверенном контуре.
- SQLAlchemy 2.x, Alembic и Pydantic 2.x; совместимые точные версии фиксируются lock-файлом.
- Один личный workspace создаётся при инициализации. Его идентификатор присутствует в данных с первого дня; интерфейс семейного доступа в первой версии отсутствует.
- Базовые справочники единиц и категорий версионируются.
- Изменения учёта проходят единый сервис команд, независимо от фото, голоса, ручного ввода или будущего импорта.
- Даты/время событий хранятся в UTC; календарные сроки сохраняются отдельно от часового пояса.
- Не требуется разделение приложения на микросервисы или полное event sourcing.

### 0.3. Входит в первую законченную версию

Вещи, категории, места хранения и контейнеры; партии и уникальные экземпляры; остатки; частичные перемещения; расход и пополнение; архив и восстановление; журнал и отмена операций; фото/текст/голос; коллажи; обязательный HITL; очередь подтверждений; гибридный поиск; сроки годности/действия; внутрисистемные уведомления; настройки; административная диагностика; резервное копирование; экспорт данных.

### 0.4. Не входит

Графики приёма лекарств; медицинские рекомендации; подбор дозировки; автоматические покупки; складская бухгалтерия; ценообразование и финансовая отчётность; полноценное семейное управление доступом в UI; предложения перестановки мебели; автоматическое дообучение модели на каждом исправлении; видеопоток; распознавание лиц; обязательная работа локальных моделей на телефоне.

### 0.5. Что определяется при развёртывании и не блокирует разработку

Адреса и секреты сервисов; GPU/VRAM; runtime и формат квантования; точные model_id; провайдер Cloud Gemma; лимиты его API; доступный push-канал; размер диска; место резервных копий. Для них предусмотрены адаптеры, параметры и диагностические проверки. Нельзя выдумывать возможности отсутствующего endpoint.

## 1. Цель продукта и обязательные инварианты

Пользователь должен получать достоверный ответ: что есть, где находится, сколько осталось и когда истекает срок. AI сокращает ввод; подтверждение человека фиксирует выбранное действие.

| Код | Инвариант |
|---|---|
| INV-01 | AI не изменяет подтверждённый предметный учёт до явного подтверждения пользователя. Черновики, задачи и технические метаданные сохранять разрешено. |
| INV-02 | Повтор одного подтверждения не создаёт повторного списания, перемещения или карточки. |
| INV-03 | Остаток не может стать отрицательным. Для неизвестного остатка требуется явное установление количества перед количественным расходом. |
| INV-04 | Перемещение сохраняет суммарное известное количество в одной базовой единице. |
| INV-05 | Разные партии, сроки, варианты и уникальные экземпляры не объединяются только по визуальной или семантической похожести. |
| INV-06 | Задача, ожидающая пользователя, не удерживает GPU, сетевой запрос к модели или транзакцию БД. |
| INV-07 | Local-only данные не поступают внешним AI-провайдерам при fallback, retry, диагностике или обновлении индекса. |
| INV-08 | Подтверждение устаревшего предложения не перезаписывает незаметно актуальные данные. |
| INV-09 | Перезапуск API/воркеров и потеря Redis не уничтожают подтверждённый учёт и сохранённую очередь проверки. |
| INV-10 | Нулевой остаток не является командой удаления истории. |
| INV-11 | Изменение административных параметров не позволяет отключить авторизацию, HITL, идемпотентность и запрет внешней передачи local-only данных. |
| INV-12 | Все операции и поисковые кандидаты ограничены workspace и правами пользователя. |
| INV-13 | Подтверждённые пользователем сведения имеют приоритет над последующими предположениями модели. |
| INV-14 | Параметры, модели, промпты и схемы, использованные задачей, воспроизводимо идентифицируются. |

Все перечисленные инварианты проверяются кодом и интеграционными тестами. Они не являются экспериментальными confidence-порогами.

## 2. Архитектура приложения

### 2.1. Компоненты

| Компонент | Ответственность |
|---|---|
| Reverse proxy | HTTPS, ограничения размера запроса, доступ к API, завершение TLS |
| FastAPI API | Аутентификация, валидация HTTP, чтение, создание задач и подтверждений |
| Application services | Команды учёта, построение HITL, версии, транзакции, права |
| PostgreSQL | Пользователи, каталог, остатки, задания, предложения, операции, настройки, outbox |
| Redis jobs | arq, временная координация, сигнализация о готовых заданиях |
| CPU workers | Медиа, предложения, применение подтверждений, индексирование, напоминания, GC |
| Local ML dispatcher | Допуск к общей GPU, выбор локального задания и контроль lease |
| Local model adapters | Проверка чувствительности, ASR, VLM, эмбеддинги |
| Cloud adapter + LiteLLM | Разрешённые внешние вызовы, бюджеты, routing, ошибки провайдера |
| Qdrant | Dense/sparse retrieval, фильтры, объединение рангов |
| MinIO | Приватные медиа, производные изображения, временные экспорты |
| Scheduler/reconciler | Периодические задачи, восстановление пропущенных запусков, очистка lease |

~~~mermaid
flowchart TD
    Client["Клиент"] --> API["FastAPI"]
    API --> App["Сервисы команд и HITL"]
    App --> PG["PostgreSQL и outbox"]
    PG --> Dispatch["Диспетчер фоновых задач"]
    Dispatch --> CPU["CPU-воркеры"]
    Dispatch --> Local["Локальная ML-очередь"]
    Dispatch --> Policy["Проверка внешней передачи"]
    Local --> GPU["Локальные модели"]
    Policy --> Cloud["LiteLLM и внешние модели"]
    CPU --> Media["MinIO"]
    CPU --> Search["Qdrant"]
    CPU --> PG
    Local --> PG
    Cloud --> PG
~~~

Qdrant, MinIO, Redis и локальные inference-endpoint не публикуются как общедоступные сервисы. Клиент обращается к разрешённым HTTP API и временным ссылкам, выданным после проверки доступа.

### 2.2. Границы модулей

Обязательные модули: auth, workspaces, catalog, locations, stock, operations, media, ingestion, inference, proposals, search, notifications, settings, admin, outbox, audit.

Маршрутизатор FastAPI не содержит логику списания или merge. Модель не получает SQL, прямой доступ к базе или произвольные инструменты. Репозитории не вызывают внешние модели.

Тяжёлая обработка изображений и синхронные вычисления не исполняются в event loop HTTP-процесса. На каждый конкурентный запрос/задачу выделяется собственная SQLAlchemy session. Транзакция не держится открытой во время инференса и ожидания пользователя.

### 2.3. Профиль первой инсталляции

Одна GPU-операция одновременно, несколько лёгких CPU-задач, один scheduler с защищённым лидерством. Маленькая и большая Gemma могут использовать одну физическую GPU; их адаптеры учитывают общий ресурс. Раздельные HTTP-endpoint моделей не означают независимую GPU-ёмкость.

Кэш списков можно отключить до измерения необходимости. Очередь проверки пользователя не ограничивается количеством активных GPU-задач.

## 3. Соглашения о данных

- Идентификаторы публичных сущностей — UUID. Примеры UUID в документе являются демонстрационными.
- В API decimal передаётся строкой, например "2.500"; float для остатков не используется.
- Количества в БД: NUMERIC(20,6); фактический шаг задаётся единицей и карточкой.
- Время событий: TIMESTAMPTZ, в API RFC 3339 с часовым поясом.
- Даты годности: DATE плюс точность day/month/unknown и исходный текст.
- Версия изменяемой сущности: положительное bigint version, увеличиваемое при изменении.
- Для таблиц workspace-данных обязателен workspace_id. Связь на объект другого workspace запрещается составными FK или эквивалентной проверкой БД.
- Имена пользователя и названия предметов не являются уникальными идентификаторами.
- Неизвестное значение обозначается null с явным состоянием; модель не заполняет отсутствующие сведения выдуманным значением.
- Nullable внешние ключи не используются для смешения «неизвестно», «не применимо» и «удалено».
- Оригинальное распознанное значение и нормализованное значение разделяются, если нормализация меняет смысл или точность.
- Генерируемое описание отмечается как generated. Его неподтверждённые утверждения не становятся фильтруемыми фактами.
- JSONB имеет versioned schema; произвольный JSON от модели напрямую в доменную таблицу не копируется.

## 4. Подробная модель данных

Ниже перечислены обязательные логические таблицы. Допускается объединение технических таблиц при сохранении их семантики, контрактов и ограничений.

### 4.1. Пользователи и доступ

| Таблица | Обязательные поля |
|---|---|
| users | id, login, password_hash, app_role(admin/user), status, locale, timezone, auth_version, created_at, updated_at |
| sessions | id, user_id, refresh_token_hash, family_id, expires_at, revoked_at, created_at |
| agreements | id, user_id, agreement_type, version, accepted_at, acceptance_context |
| workspaces | id, name, owner_user_id, version, created_at |
| workspace_memberships | workspace_id, user_id, role(owner/editor/viewer), status |
| user_preferences | user_id, version, schema_version, values JSONB, updated_at |

Первый пользователь создаётся bootstrap CLI. Открытая регистрация отключена. Единственный workspace создаётся автоматически; membership owner добавляется ему же. Глобальная роль admin не выводится автоматически из роли владельца любого workspace.

### 4.2. Места хранения

locations:
- id, workspace_id, parent_id, name, description, kind(place/container/system_unspecified);
- version, created_at, updated_at, archived_at;
- default_privacy_policy(cloud_allowed/local_only), nullable.

В каждом workspace создаётся ровно одно системное место «Место не указано». Оно нельзя удалить, вложить в другое место или сделать родителем. Это место используется вместо null в остатках.

Иерархия поддерживается в данных. Максимальная глубина является параметром. Запрещены циклы, перенос в собственного потомка и parent из другого workspace. Перемещение контейнера меняет parent_id, не переписывая location_id всех вещей внутри. Полный путь вычисляется по дереву или восстанавливаемому path-кэшу.

Архивация непустой локации требует выбранной стратегии переноса; для сохранённых ссылок истории используется снимок названия/пути без обязательного вечного хранения удалённой локации.

### 4.3. Карточки вещей

items:
- id, workspace_id, name, primary_category, secondary_categories;
- tracking_mode(individual/counted/measured/untracked);
- base_unit_id, quantity_step, attributes JSONB, attributes_schema_version;
- barcode, brand, model, tags;
- user_description, generated_description, description_model_revision;
- privacy_policy(cloud_allowed/local_only);
- lifecycle(active/archived/deleted), version;
- created_by, created_at, updated_at, archived_at, deleted_at;
- search_revision, indexed_revision.

Карточка counted/measured описывает вариант: конкретный размер, модель, дозировку, цвет и другие значимые отличия. Для уникального предмета создаётся individual-карточка; два серийных экземпляра не сливаются в один individual.

Данные документа, серийный номер конкретного экземпляра и срок конкретной упаковки хранятся на экземпляре/партии, а не смешиваются в общей карточке нескольких упаковок.

Неизвестное название допускает системный временный заголовок «Неопознанный предмет — дата/номер». Такой заголовок не считается результатом распознавания. Пользователь может подтвердить фотокарточку и уточнить её позже.

### 4.4. Партии, упаковки и экземпляры

lots:
- id, workspace_id, item_id, lot_kind(batch/instance/untracked);
- label, serial_number, manufacturer_batch, parent_lot_id;
- acquired_at, manufactured_on, opened_on;
- expiry_on, expiry_precision(day/month/unknown), expiry_raw_text;
- after_opening_amount, after_opening_unit(day/month), effective_expiry_on;
- expiry_derivation(explicit/normalized_month/after_opening/minimum/unknown);
- privacy_policy, attributes JSONB, attributes_schema_version;
- version, created_at, updated_at, archived_at.

У item всегда есть минимум один lot после первого подтверждённого добавления. Для вещи без срока допускается неограниченная по сроку партия. Для individual создаётся один instance-lot.

Новое поступление по умолчанию создаёт новую партию, если отличаются срок, открытие, состояние, идентификатор упаковки или режим приватности. Слияние партий разрешается только явной операцией после проверки совместимости и сохранения происхождения.

Если одинаковая закрытая партия содержит несколько упаковок, открытие одной упаковки может требовать отделения соответствующего количества в новый lot. На одну партию нельзя записать дату открытия, относящуюся лишь к части её остатка.

### 4.5. Остатки и присутствие

stock_balances:
- id, workspace_id, lot_id, location_id;
- quantity NUMERIC(20,6), nullable;
- quantity_state(exact/estimated/unknown/not_applicable);
- version, last_confirmed_at, last_confirmed_by, updated_at.

Уникальность: workspace_id + lot_id + location_id.

| Режим | Правило |
|---|---|
| counted | Количество в базовых единицах; шаг обычно целый, иной шаг явно разрешён карточкой |
| measured | Количество decimal с известной единицей и шагом |
| individual | Один instance-lot, количество 1 в одном месте либо 0 после списания; произвольное дробление запрещено |
| untracked | quantity=null, quantity_state=not_applicable; одна запись присутствия на lot; перемещение целиком |
| unknown | quantity=null, количественный расход запрещён до явного установления остатка |
| estimated | Число сохраняется как оценка; результаты операций сохраняют отметку оценочности |

CHECK: известное количество >= 0. Для unknown/not_applicable quantity должно быть null. Для exact/estimated quantity обязательно.

Агрегат карточки возвращает known_quantity, has_unknown_quantity и is_estimated. При неизвестных остатках нельзя показывать сумму известных как точный полный остаток. Признак depleted вычисляется только для количественного учёта: нет положительных и нет неизвестных остатков. Нулевые записи разрешено сохранять для истории и версий.

### 4.6. Единицы и преобразования

Конверсия кг↔г и л↔мл выполняется детерминированно. «Упаковка» преобразуется в базовую единицу только при заданном package_size. «Пара» не равна «штука» без явного правила. Миллиграммы действующего вещества не преобразуются автоматически в количество таблеток. Изменение базовой единицы после операций требует отдельной миграционной команды с просмотром результата.

### 5.2. Создание карточки и поступление

NewItemSpec содержит имя, tracking_mode, единицу, категорию, атрибуты и policy. NewLotSpec содержит тип партии, срок, открытие и атрибуты экземпляра. Сервер генерирует идентификаторы; существующие идентификаторы принимает только после проверки workspace.

Штрихкод предлагает кандидата карточки. Совпадение штрихкода не доказывает совпадение срока конкретной упаковки. Новая поставка может присоединиться к партии только при явном выборе и совместимости атрибутов.

Если название, срок или остаток неизвестны, UI предлагает «Оставить неизвестным». Такой выбор не блокирует добавление фотокарточки. Неизвестная единица не преобразуется в «шт.» без отражённого в форме решения.

### 5.3. Расход и выбор партии

Если есть несколько партий или мест, backend возвращает варианты с фото, остатком, полным путём и сроком. Можно предложить первым ближайший известный срок, но пользователь видит выбранную партию до подтверждения. Отсутствие срока не означает максимальную свежесть.

Расход из нескольких партий допускается как несколько действий одного предложения. Backend показывает распределение количеств. Нельзя незаметно дописать списание из другой партии, если выбранной не хватает.

### 5.4. Перемещение

Частичный перенос блокирует затронутые балансы, уменьшает источник, увеличивает назначение и записывает журнал одной транзакцией. Если назначения ещё нет, создаёт баланс с уникальностью lot+location.

Источник и назначение совпадают: команда является no-op с понятным сообщением, не создаёт искусственного движения. При переносе контейнера изменяется только дерево мест; поисковые пути и кэши обновляются фоново.

Для untracked перемещается запись присутствия. Для unknown количества разрешён перенос целого неизвестного остатка только при явном выборе «переместить целиком»; частичный расход или перенос требует сначала определить количество.

При объединении exact+exact результат exact; при участии estimated результат estimated. Unknown нельзя молча складывать с известным числом и терять это число. Если в назначении уже есть известный остаток того же lot, форма предлагает либо явно установить общий остаток, либо выделить переносимую неизвестную часть в отдельный lot с сохранением происхождения. Выбор входит в подтверждаемое предложение. Неизвестное количество не преобразуется автоматически в ноль.

### 5.5. Поправки и отмена

Отмена создаёт новую предложенную обратную операцию. Исходный журнал не стирается. Если после исходного перемещения часть вещей израсходована, автоматическая обратная операция может быть невыполнима; возвращается форма разрешения конфликта.

Сроки и названия можно восстановить только если это не перезапишет более новое изменение без подтверждения. Окончательное удаление приватных данных не позиционируется как отменяемая операция.

### 5.6. Идемпотентность

Каждый POST, создающий задачу, предложение, подтверждение, экспорт, purge или изменение параметров, поддерживает Idempotency-Key. Область ключа: user_id + workspace_id + endpoint_operation.

Сервер сохраняет canonical request hash. Одинаковый ключ и одинаковое тело возвращают прежний идентификатор и результат. Одинаковый ключ с другим телом — 409 IDEMPOTENCY_KEY_REUSED.

Для подтверждения дополнительно действует уникальность proposal_id + proposal_revision. Случайная смена ключа клиентом не должна позволить применить одну ревизию повторно.

Временная таблица транспортных ключей может очищаться. Уникальность подтверждённой ревизии и operation_id хранится столько же, сколько запись операции. На одну лишь уникальность arq job_id полагаться нельзя: [arq допускает повторное выполнение задания](https://github.com/python-arq/arq/blob/main/docs/index.rst).

### 5.7. Чтение и неподдерживаемые команды

Чистый поиск или ответ «где находится» не изменяет предметный учёт и не требует подтверждения. Если голосовая задача определена как read-only, она может завершиться succeeded с search result вместо proposal. Перед выдачей результата действуют обычные права и policy.

Если запрос смешивает чтение и изменение, ответ разделяет найденные сведения и неподтверждённую операцию. Неизвестный intent возвращает выбор поддерживаемых действий; произвольный текст модели не становится новой исполняемой командой.

## 6. Жизненный цикл задачи

### 6.1. Состояния tasks

| Состояние | Смысл | Допустимый следующий шаг |
|---|---|---|
| accepted | Вход и ссылка на медиа сохранены | preparing, cancelled, failed |
| preparing | Проверка и подготовка медиа | queued, waiting_for_review, failed, cancelled |
| queued | Ожидается ML-ресурс или очередной ML-этап | running, cancelled, expired |
| running | Выполняется ограниченный по времени ML-этап | queued, retry_wait, waiting_for_review, succeeded для read-only, failed, cancelled |
| retry_wait | Ожидается разрешённая повторная попытка | queued, failed, cancelled, expired |
| waiting_for_review | Есть сохранённое предложение и форма | applying, cancelled, expired |
| applying | Подтверждение принято, запись поставлена в CPU-очередь или выполняется | succeeded, waiting_for_review, failed |
| succeeded | Все действия подтверждённого предложения применены | Терминальное состояние |
| failed | Технически завершено с ошибкой | До принятия confirm: новый retry-task/ручная форма; после confirm: только явный retry того же confirmation |
| cancelled | Обработка/проверка отменена до принятия подтверждения | Терминальное состояние |
| expired | Истёк срок хранения незавершённой задачи | Терминальное состояние |

running может переходить в queued между стадиями: GPU освобождена, результат стадии сохранён, следующая стадия имеет отдельный job. Текущий stage указывает privacy_asr, extraction, candidate_selection и т. п.

Состояние waiting_for_review не обязательно означает, что уже можно подтвердить: форма может иметь blocking_issues и can_confirm=false. Все варианты устранения блокеров возвращаются в той же форме.

### 6.2. Поля tasks

id, workspace_id, created_by, client_request_id, parent_task_id, batch_id, input_mode, input_text, media_ids, audio_media_id, context_location_id, context_item_id, requested_privacy, effective_privacy, status, stage, status_version, queue_class, priority, config_revision, config_snapshot_hash, model_route_revision, prompt_revision, output_schema_version, attempt_count, next_attempt_at, deadline_at, lease_owner, lease_until, fencing_token, heartbeat_at, progress JSONB, proposal_id, result JSONB для read-only, cancel_requested_at, error_code, error_details_sanitized, created_at, updated_at, completed_at.

Текст и транскрипт хранятся по политике retention. После их удаления сохраняются технические метаданные и достаточные для истории подтверждённые результаты.

### 6.3. Предложения и их ревизии

Предложение имеет status: editable, confirming, applied, superseded, cancelled, expired. Каждое изменение значимых values, зависимостей или формы создаёт новую revision и новый review_hash.

В каждый момент у обычной задачи только одно активное предложение. Предыдущие ревизии доступны диагностике в рамках retention. Результат старой ML-попытки не заменяет новую пользовательскую правку: запись результата требует совпадения fencing_token и ожидаемой ревизии.

### 6.4. Возобновление

- Завершённая стадия сохраняется в PostgreSQL до следующего dispatch.
- Повторный job сначала проверяет актуальный статус и уже сохранённый результат.
- Reconciler находит задания без действующего lease и восстанавливает постановку.
- Потеря Redis восстанавливается из durable tasks, confirmations и outbox.
- Истёкший lease не означает, что физическая GPU уже свободна: адаптер должен подтвердить завершение/остановку запроса либо supervisor восстановить inference-сервис.
- Отменённая задача не принимает поздний результат; он может быть сохранён только как технический факт и очищен позже.

### 6.5. Ошибки и ручное продолжение

Ошибка распознавания не должна уничтожать фото. Пользователь может открыть ручную форму на основе тех же материалов, выбрать карточку или оставить часть сведений неизвестной. Новый task ссылается на исходный через parent_task_id и не копирует байты медиа без необходимости.

### 6.6. Повтор после принятого подтверждения

Ошибка применения отличается от ошибки распознавания. После принятого confirm новый ML-task не создаётся автоматически: это могло бы сформировать второе списание того же намерения.

POST /confirmations/{id}/retry повторно ставит тот же confirmation со старым operation_id после проверки прав и состояния. Если операция уже обнаружена в БД, возвращается applied. Если её нет, разрешённый retry переводит failed confirmation в queued, связанную task — в applying и сохраняет audit. Актуальные остатки всё равно перепроверяются; при изменении зависимостей создаётся новая review revision.

Терминальная failed confirmation не обрабатывается опоздавшим worker без нового разрешённого dispatch/fencing. POST /tasks/{id}/retry и manual-review применяются к ошибкам до принятия подтверждения. Для уже применённой операции используется reverse-preview либо явно новая пользовательская команда.

## 7. Главный контракт HITL: предзаполненная форма

### 7.1. Принцип

Backend возвращает не свободный текст с вопросами, а versioned review document. Этот документ содержит:

1. Понятное резюме действия и предмета.
2. Предпросмотр изменения: что создаётся, откуда/куда переносится, сколько было и станет.
3. Типизированные значения полей.
4. UI-описание из разрешённого набора контролов.
5. Кандидатов для неоднозначных полей.
6. Blocking issues и неблокирующие предупреждения.
7. Источники значений и фрагменты фото для проверки.
8. Допустимые действия и причины недоступности подтверждения.
9. Ревизию и review_hash для защиты от подтверждения другого состояния.

UI-описание формируется приложением по шаблонам категорий и операций. Модель выдаёт семантические данные; она не генерирует HTML, JavaScript, URL методов, JSON Schema или произвольный layout.

### 7.2. Разрешённые контролы

| Контрол | Применение |
|---|---|
| entity_picker | Выбор существующей карточки, партии, источника |
| location_picker | Выбор места из дерева; недавние места в начале |
| segmented_control | «Новая вещь / существующая», режим количества, вариант операции |
| number_stepper | Списание, пополнение, число штук |
| decimal_input | Измеряемые остатки с фиксированным шагом |
| unit_select | Совместимые единицы |
| date_picker / month_picker | Срок и дата открытия с точностью |
| checkbox / switch | Подтверждение неизвестного значения, режим local-only, дополнительный атрибут |
| chips_select | Категория, теги, варианты цвета/размера |
| candidate_cards | Несколько объектов с фотографиями и ключевыми отличиями |
| photo_region | Просмотр участка этикетки, не поле произвольной команды |
| text_input | Название/описание как запасной способ исправления |

У контролов есть stable key, action_id, label, value_type, required, editable, options, validation, source, verification_state, importance. Порядок полей определяется UI-шаблоном, а не порядком JSON.

Простые условия visible_when/required_when используют только разрешённые операторы eq/in/not_empty над известными ключами. Выполнение кода из условий запрещено.

### 7.3. Приоритет предзаполнения

1. Явное значение пользователя в текущем вводе.
2. Подтверждённый контекст: открытая карточка/локация, выбранная партия.
3. Существующие подтверждённые данные выбранной сущности.
4. Извлечённые и нормализованные данные фото/аудио.
5. Явно показанная безопасная настройка по умолчанию.
6. Неизвестно.

Если источники противоречат друг другу, UI показывает варианты и источник конфликта. Модель не перезаписывает молча введённую пользователем дату.

Необязательные неизвестные поля не требуют текста. Для обязательного идентификатора существующего объекта предлагаются карточки; для неизвестного количества — «Учесть без точного остатка», если операция это допускает. Для расхода неизвестного остатка нужен выбор известной партии либо ввод/выбор остатка.

### 7.4. Минимизация действий

Обычная готовая форма подтверждается одной кнопкой «Подтвердить». Пользователь не обязан нажимать отдельный чекбокс у каждого корректно заполненного поля.

При неоднозначности наушников достаточно выбрать одну из карточек. При количестве 19 вместо 20 достаточно одного шага счётчика. При неверном месте — выбрать место. Повторный ML-вызов для этих действий не требуется.

Отдельное подтверждение каждого распознанного атрибута не вводится по умолчанию. Критические неоднозначные поля блокируют общую кнопку до выбора. Факт общего подтверждения фиксирует принятие видимых значений формы, включая дату, единицу, выбранную партию и внешний режим обработки.

Нельзя требовать повторный снимок только из-за неизвестного необязательного атрибута. Приложение предлагает сохранить с неизвестным значением и исправить позже.

### 7.6. Изменение полей

PATCH /api/v1/proposals/{id}:
- expected_revision;
- changes — список action_id/key/value из разрешённой схемы;
- idempotency key.

~~~json
{
  "expected_revision": 1,
  "changes": [
    {"action_id": "a1", "key": "quantity", "value": "19"},
    {
      "action_id": "a1",
      "key": "location_id",
      "value": "00000000-0000-4000-8000-000000000051"
    }
  ]
}
~~~

Ответ — новая полная форма с revision=2, пересчитанным preview и review_hash. Неизвестные поля запрещены. Смена карточки или партии пересчитывает зависимые значения, но не стирает явно введённые сведения без отражённого конфликта.

Действия UI могут отправляться debounce, однако несохранённые изменения обязательно входят в подтверждение. Потерянный PATCH не должен привести к подтверждению старых значений.

### 7.7. Подтверждение одним запросом

POST /api/v1/proposals/{id}/confirm принимает expected_revision, observed_review_hash, optional changes и client_request_id. Header Idempotency-Key обязателен.

~~~json
{
  "expected_revision": 1,
  "observed_review_hash": "sha256:example-review-digest",
  "client_request_id": "00000000-0000-4000-8000-000000000070",
  "changes": [
    {"action_id": "a1", "key": "quantity", "value": "19"}
  ]
}
~~~

Если changes содержат только явно выбранные допустимые поправки, сервер применяет их к предложению, валидирует результат и принимает подтверждение за один запрос. Он не запускает новую модель.

Если поправка создаёт новую неоднозначность или изменились другие существенные зависимости, возвращается 409 REVIEW_UPDATE_REQUIRED с новой формой. До повторного подтверждения никакой записи в учёт нет.

Успешный приём: 202, confirmation_id, task_id, status=queued, poll_after_ms. Это означает «подтверждение принято», а не «учёт уже изменён».

### 7.8. Обработка подтверждения

Транзакция приёма:
1. Проверить ключ идемпотентности.
2. Заблокировать task и proposal.
3. Проверить пользователя, статус, revision, observed_review_hash и отсутствие принятого подтверждения.
4. Нормализовать явно переданные changes и проверить форму.
5. Создать review_receipt и confirmation со стабильным operation_id.
6. Proposal перевести в confirming, task — в applying.
7. Записать outbox для CPU-применения и commit.

Транзакция применения:
1. Заблокировать confirmation; если applied — вернуть сохранённый результат.
2. Заблокировать затронутые строки в стабильном порядке UUID.
3. Проверить версии и актуальные бизнес-условия.
4. Выполнить все действия одного предложения атомарно.
5. Записать operations, entries и outbox индекса/напоминаний/кэша.
6. Mark confirmation applied, proposal applied, task succeeded.
7. Commit; только после этого сообщать об успешном изменении.

При конфликте никакие предметные изменения не коммитятся. В отдельной короткой транзакции сохраняется новая ревизия формы; прежнее confirmation получает conflict, task возвращается waiting_for_review. Review receipt сохраняется как факт того, что прежнее предложение было принято, но не применено.

Технический повтор после сбоя использует прежний confirmation_id и operation_id.

### 7.9. Очередь проверки и пакетное подтверждение

GET /api/v1/review-inbox возвращает все waiting_for_review с summary, thumbnail, количеством блокеров, возрастом, effective_privacy и ссылкой на форму. Сортировки: время создания, готовые сначала, ошибки/уточнения сначала. Фильтры: batch_id, категория, место, состояние.

Для независимых предложений допускается batch-confirm с отдельным результатом каждого элемента. Нельзя возвращать один success, если часть не применена.

Для связанных предложений, затрагивающих один остаток, предусмотрен POST /api/v1/review-batches:
- принимает список proposal_id/revision;
- строит новое объединённое предложение по актуальным остаткам;
- показывает суммарный расход/перенос и порядок действий;
- сохраняет source_proposal_ids и source_revisions;
- не изменяет оригинальные предложения до принятия общего подтверждения.

Объединённое предложение подтверждается обычным confirm. При приёме блокируются также исходные предложения; проверяется, что ни одно не изменено/не подтверждено отдельно. Все исходные задачи переходят applying, после атомарного применения — succeeded. Альтернативное подтверждение любого источника получает конфликт. Неиспользованный batch-preview не блокирует обычную работу бесконечно.

Таким образом, несколько списаний одной партии можно проверить общим итогом без серии заведомо устаревающих форм. Максимальный размер объединения настраивается.

## 8. Приём и хранение медиа

### 8.1. Протокол загрузки

Первая версия использует POST /api/v1/media с multipart upload по HTTPS. Ответ после успешной записи объекта и строки БД: 201, media_id, state=uploaded, type и метаданные. Для больших загрузок позднее можно добавить выдачу upload URL, сохранив обязательный finalize с проверкой фактического объекта.

Порядок:
1. Аутентификация и workspace.
2. Проверка лимита числа/размера файлов и типа содержимого.
3. Запись в временный object_key.
4. SHA-256, MIME sniffing, безопасное декодирование, контроль числа пикселей/длительности.
5. Сохранение media_assets; привязка к задаче выполняется отдельным шагом.
6. Производные файлы создаются воркером.
7. Незавершённые временные объекты собираются GC после configured TTL.

Нельзя возвращать успешный media_id до завершения записи bytes. При падении между объектом и строкой БД временный объект подбирается reconciler/GC. Пользователь не передаёт произвольный URL для серверного скачивания.

### 8.2. Виды медиа и версии

source — именно полученный от клиента файл, возможно уже сжатый; normalized — повёрнутая/очищенная копия; thumbnail — превью; collage — вход локальной VLM; crop — фрагмент этикетки; normalized_audio — внутренний формат ASR.

Термин RAW не используется для заведомо сжатого клиентского JPEG. Сохраняется признак client_preprocessed. Исходные принятые фотографии остаются отдельными файлами и не заменяются только коллажем.

Первая версия допускает JPEG/PNG/WebP после проверки декодера. HEIC добавляется через отдельный проверенный адаптер или предварительную конверсию клиента. Аудиоформаты объявляются endpoint capabilities; внутренний ASR-формат — mono PCM 16 kHz WAV, если это подтверждённое требование runtime. Нормализация на сервере позволяет позднее принимать другие клиентские контейнеры без изменения доменного API.

### 8.3. Ограничения

Настраиваются количество фото на задачу, bytes на файл/задачу, декодированные пиксели, длительность аудио, число производных и общий дисковый бюджет. Разрешённое число исходных фото не равно разрешённому числу изображений в ML-запросе.

Проверка декодированных пикселей защищает процесс от случайно огромного изображения. EXIF orientation применяется перед удалением лишних метаданных. Геолокация EXIF не используется как автоматически подтверждённое место хранения.

### 8.4. Доступ и удаление

В таблице хранится object_key, а не постоянный общедоступный URL. GET /media/{id}/download выдаёт короткоживущую ссылку или проксирует байты после проверки workspace и policy.

Source, collage, crop и thumbnail наследуют наиболее строгую policy всех исходников. Приватное превью остаётся приватным. Хранилище обслуживается внутри доверенного контура.

Удаление reference и удаление bytes разделены. Файл не удаляется, пока нужен другой активной карточке или незавершённой задаче. Проверка использует фактические связи, а не только легко рассинхронизируемый счётчик.

## 9. Коллаж для локальной Gemma

### 9.1. Обязательное поведение

В каждом запросе к текущему локальному image-endpoint содержится ровно один image input. Для нескольких источников это один сгенерированный коллаж. Адаптер отклоняет попытку отправить два image input независимо от промпта.

Если выбранный endpoint позднее научится принимать несколько изображений, это включается через проверенную capability и новую версию preprocessing; существующие задачи сохраняют свой snapshot.

### 9.2. Алгоритм

1. Прочитать упорядоченный список media_id; применить EXIF orientation.
2. Нормализовать цвет и альфа-канал, сохранить пропорции.
3. Для одного фото использовать нормализованное изображение в допустимом canvas.
4. Для нескольких выбрать детерминированную сетку из разрешённых шаблонов, максимизирующую читаемую площадь при ограничении canvas.
5. Масштабировать с сохранением пропорций; LANCZOS — стартовый ресэмплер.
6. Использовать padding/letterbox; важные края упаковки не обрезать автоматически.
7. Пронумеровать области «Фото 1», «Фото 2» в отдельной полосе, не перекрывающей содержимое.
8. Добавить manifest с координатами плиток, padding, масштабом и media_id.
9. Сохранить collage object, manifest, config_revision и preprocessing_version.
10. Отправить модели одну картинку и текстовый список областей.

Изменение порядка снимков или параметров меняет производный cache key. Отдельный номер области не является пользовательскими данными для определения предмета.

~~~json

  "canvas_height": 1200,
  "preprocessing_version": "collage-1",
  "tiles": [

      "index": 1,
      "media_id": "00000000-0000-4000-8000-000000000031",
      "rect": {"x": 0, "y": 32, "width": 800, "height": 1168},

      "normalized_source_height": 1920,
      "scale": 0.4
    },
    {
      "index": 2,
      "media_id": "00000000-0000-4000-8000-000000000032",

Цифры демонстрируют формат и не являются рекомендуемым разрешением для любого GPU. При преобразовании координат обратно в source учитываются content_rect и scale. Полоса номера и padding не могут использоваться как доказательство атрибута.

### 9.4. Когда текст слишком мелкий

Backend не должен бесконечно ухудшать все фото, чтобы втиснуть их в фиксированный маленький коллаж. Допустимы:
- один обзорный коллаж для классификации;
- последующий локальный вызов с одним crop или одним detail-collage;
- отдельные последовательные вызовы по одному изображению, если разрешены лимитом попыток;
- форма с неизвестным значением, где показан исходный крупный фрагмент.

Все эти вызовы сохраняют ограничение «одно изображение за раз». Пользователь не обязан заново фотографировать читаемый исходник только потому, что первый коллаж слишком мал.

Лимит detail-pass, минимальная сторона плитки, максимальный canvas и бюджет visual tokens настраиваются. Если внутренний image processor runtime всё равно уменьшает картинку, реальная читаемость проверяется на его входе, а не только по размеру JPEG.

### 9.5. Контекст

8192 токена допустимы как стартовый бюджет сервиса, но не считаются фундаментальным ограничением семейства Gemma. По [карточке Gemma 4](https://ai.google.dev/gemma/docs/core/model_card_4) контекст и аудиовозможности различаются между вариантами; 31B не принимает аудио. Реестр локальных endpoint обязан содержать отдельно заявленные и проверенные runtime capabilities.

Бюджет учитывает system prompt, инструкцию, кандидатов, изображения/аудио, ожидаемый JSON и резерв на ответ. Перед отправкой сокращаются необязательные описания кандидатов; подтверждённые идентификаторы и критические отличия не отбрасываются ради лимита. Усечение фиксируется в task_attempts.

## 10. Локальный ASR и первичная проверка

Аудио поступает только в доверенный контур до определения effective_privacy. GigaAM отсутствует в зависимостях, схемах и настройках.

Если runtime поддерживает совместный audio+image input, первичная Gemma может вернуть транскрипт и privacy-классификацию вместе. Если совместный ввод не поддерживается, адаптер выполняет последовательные локальные вызовы: ASR, затем анализ текста и одного изображения. Архитектура не предполагает неподтверждённую мультимодальную комбинацию.

Первичный результат:
- transcript и язык;
- текстовые/визуальные признаки для поиска кандидатов;
- privacy_decision: sensitive/non_sensitive/uncertain;
- обнаруженные типы чувствительности без необходимости дублировать все исходные номера;
- признаки недостаточного качества;
- список конфликтующих/неизвестных сведений;
- provenance.

При длинном аудио применяется разрешённая runtime длительность сегмента, небольшой overlap и детерминированное соединение без двойного повторения фраз. Если runtime не поддерживает нужную длину, это ошибка capabilities, а не повод направить private-аудио в облако.

Транскрипт может быть отредактирован, но стандартное исправление происходит через итоговые структурированные поля. Отрицания, будущие намерения и цитаты не преобразуются автоматически в совершённые операции.

## 11. Приватность и маршрутизация моделей

### 11.1. Граница доверия

Владелец доверяет своему серверу. Передача фото, документов и аудио этому серверу является штатной частью работы. PostgreSQL, MinIO, Redis, Qdrant, локальные inference-процессы, резервные копии в согласованном контуре и локальная диагностика входят в серверный контур.

Соглашение фиксируется для будущих пользователей через versioned agreement. Для владельца первоначальная настройка сохраняет принятую конфигурацию; дополнительные запросы согласия на каждую локальную обработку не нужны.

### 11.2. Вычисление effective_privacy

Режим local_only включается, если выполнено хотя бы одно:
- глобально запрещены внешние модели;
- пользователь передал force_local;
- входное медиа/существующая карточка/партия имеет local_only;
- задействованная локация принудительно local_only;
- распознан документ или чувствительные сведения;
- первичная проверка дала uncertain либо технически не завершилась.

Иначе режим cloud_allowed означает разрешение, но не обязанность обращаться вовне. Пользовательская настройка «предпочитать локальную обработку» отдельно управляет маршрутом и не смешивается с обязательным запретом.

Для mixed-input применяется наиболее строгая policy всего запроса. Перед каждым внешним вызовом повторно проверяются policy payload и всех retrieval-кандидатов. Нельзя включить private-карточку в разрешённый запрос только потому, что исходная фраза была обычной.

Классификатор является дополнительным барьером и может ошибаться. Гарантия полного отсутствия внешней передачи обеспечивается явным local_only, а не обещанием безошибочной классификации. Для документов local_only обязателен по правилам продукта.

### 11.3. Изменение policy

Усиление policy действует немедленно на новые исходящие вызовы уже созданных задач. Ослабление допускается только явным действием пользователя/администратора в пределах разрешённых правил и не отменяет уже установленный строгий запрет документа.

Нельзя сделать незаметный fallback из local_only в cloud_allowed. Изменение обычной настройки маршрута не отменяет snapshot задачи, кроме явно описанных аварийных запретов.

### 11.4. Реестр моделей

model_routes / deployments содержат:
- logical_name: privacy_asr, local_vlm, cloud_primary, cloud_fallback, embeddings;
- provider, actual_model_id, deployment_id, endpoint_ref, credential_ref;
- trust_domain(local/external), enabled, maintenance;
- modalities, supports_combined_audio_image, max_images_per_request;
- context_budget, max_output_tokens, supported_json_mode;
- audio_max_seconds, image_preprocessor_revision;
- timeout, max_attempts, cooldown policy;
- price_metadata и дата его актуальности, если доступны;
- runtime/version/quantization и проверенные capabilities.

Секреты не возвращаются административному UI. Вместо них отображается credential_ref и результат подключения.

### 11.5. Маршруты

| Условие | Маршрут |
|---|---|
| force_local или sensitive/uncertain | Локальная первичная стадия → локальная VLM → форма |
| cloud_allowed + strategy=local_first | Локальная стадия → local_vlm → разрешённый cloud fallback при конкретной проблеме |
| cloud_allowed + strategy=cloud_preferred | Локальная первичная стадия → cloud_primary → разрешённый fallback |
| Выбранная карточка + явные поля ручной формы | Детерминированный command builder без ML |
| Модель не может выбрать из нескольких подходящих существующих вещей | Candidate picker в форме |
| Кончился бюджет/попытки | Частично заполненная форма или понятная ошибка с ручным продолжением |
| Все локальные модели недоступны и local_only | Ожидание/ошибка/ручная форма; внешнего вызова нет |

Fallback выбирается по типу неудачи: недопустимый JSON, нечитаемый фрагмент, временная недоступность или нехватка возможностей. Он не должен пытаться «угадать» физическое действие, сведений о котором нет.

### 11.6. Формат ответа модели

Версионируемая схема extraction.v1 содержит intent_candidates, extracted_entities, fields, evidence, ambiguity, privacy_signals и quality_issues. Все значения проходят Pydantic-валидацию; неизвестные ключи запрещены.

LLM выбирает только из предоставленных candidate_id или указывает unknown/new. Выдуманный существующий UUID отклоняется. Numeric self-confidence необязателен; если он есть, это diagnostic_score, не разрешение применить действие.

При повреждённом JSON допустима ограниченная repair-попытка с той же или разрешённой другой моделью. Результат eval/code execution не используется для разбора ответа. Граница между пользовательским текстом и системной инструкцией сохраняется.

Версии prompt templates хранятся в репозитории и включаются в сборку; необязательный административный выбор доступен только среди зарегистрированных версий.

## 12. LiteLLM, внешние API и сетевой маршрут

LiteLLM используется как адаптер внешней маршрутизации, cooldown и учёта вызовов. Его конфигурация сама по себе не заменяет policy-check приложения и общий бюджет задачи. Возможности retries/fallback/Redis tracking описаны в [документации LiteLLM](https://docs.litellm.ai/docs/routing); точный набор параметров проверяется для закреплённой версии.

### 12.1. Классификация ошибок

| Ошибка | Действие |
|---|---|
| timeout/network/5xx | Ограниченный повтор с backoff+jitter; затем разрешённый fallback |
| 429 minute/token rate limit | Retry-After или расчёт ближайшего окна, краткий cooldown |
| 429 daily quota | Блокировка соответствующей квоты до вычисленного reset_at |
| 401/403 credentials/access | Deployment unhealthy; уведомление администратору, без бесконечного retry |
| 400 invalid input/context | Исправление подготовки или форма ошибки; не перебор ключей вслепую |
| unsupported modality | Отключить несовместимый маршрут для задачи; capability error |
| safety/refusal | Сохранить нормализованную причину; ручная форма; без попытки скрыто обойти policy |

По [документации Gemini](https://ai.google.dev/gemini-api/docs/rate-limits), лимиты применяются на проект, а дневные RPD сбрасываются в полночь Pacific Time. Ключи одного проекта не считаются независимыми квотами. Сброс рассчитывается через IANA timezone America/Los_Angeles с учётом DST; фиксированная очистка в 10:05 МСК не используется.

Cooldown хранится по provider/project/model/quota_dimension с reason и reset_at. Блокировка неисправных credentials не снимается дневным сбросом квоты. При восстановлении Redis состояние квот восстанавливается из доступного durable snapshot и осторожного health probe; задачи не отправляются массово только из-за пустого кэша.

### 12.2. Общий бюджет

У задачи есть max_total_attempts, max_external_calls, max_total_external_cost и deadline. Каждая разрешённая попытка резервирует бюджет до dispatch, фактический расход фиксируется после ответа. Неизвестная фактическая цена отмечается unknown, а не ноль.

Повтор API gateway и повтор application worker не должны перемножаться без общего счётчика. За retry отвечает один согласованный слой; внутренние retries SDK учитываются либо отключаются.

Для локальных таймаутов бюджет running-времени и абсолютный next_attempt_at хранятся раздельно. Длительное ожидание GPU и человека не расходует лимит одного inference-вызова; общий предел обработки имеет явно заданную семантику elapsed_processing_seconds. Если нужен предельный возраст задания, он задаётся отдельным task_age_limit, а не скрытым HTTP timeout.

### 12.3. Прокси

Внешние соединения могут использовать настроенный владельцем SOCKS5/HTTP-транспорт. Proxy endpoint и секреты задаются серверной конфигурацией. Backend не принимает их из обычного пользовательского запроса.

Локальные адреса исключены из внешнего proxy-маршрута. Поддержка конкретного proxy-протокола проверяется на реальном HTTP-клиенте LiteLLM/провайдера. Сетевой proxy не меняет статус внешнего провайдера на доверенный локальный.

Устаревшие model_id не зашиваются в код. Перед включением deployment выполняется capabilities smoke test. Сроки доступности сверяются с [официальным реестром снятия моделей Gemini](https://ai.google.dev/gemini-api/docs/deprecations).

## 13. Очереди, GPU и планирование

### 13.1. Классы задач

- high_priority: применение подтверждений и лёгкие действия пользователя; CPU-only.
- default: обычные локальные ML-этапы.
- bulk: массовое добавление/длинные локальные этапы.
- maintenance: индекс, GC, экспорты, сверка и напоминания; CPU, с отдельными лимитами.
- cloud: внешние HTTP-вызовы с контролем бюджета; не занимают local GPU slot.

Названия — логические классы. arq worker может обслуживать конкретную физическую очередь; weighted scheduling реализуется явным диспетчером, а не предполагаемой магической настройкой трёх Redis-списков.

### 13.2. Стартовый режим одного пользователя

Диспетчер выбирает готовое ML-задание из PostgreSQL, резервирует GPU slot и ставит один коротко ограниченный job в рабочую ML-очередь. При одном slot local concurrency=1.

Default и bulk могут обслуживаться в FIFO или с настраиваемым весом. Пользователь вручную повышает приоритет своей задачи. WAITING_FOR_REVIEW не считается занятой GPU и не участвует в active inference limit.

Маршрутизация по числу задач учитывает queued+running, а не только processing>5. Порог назначения bulk — экспериментальная настройка, не средство изоляции пользователей.

### 13.3. Lease и fencing

Lease имеет owner, expires_at и fencing_token. Heartbeat обновляет только владелец текущего token. Поздний результат старого владельца не записывает новое состояние.

Watchdog различает:
- падение application worker;
- зависший HTTP-запрос;
- продолжающийся inference на сервере;
- ожидание загрузки модели.

После отмены пользовательская задача может стать cancelled, но GPU slot освобождается физически только после подтверждённого окончания/остановки инференса. Иначе новый запрос создаст скрытую перегрузку. Для зависшего inference предусмотрен управляемый restart адаптера/сервиса администратором.

### 13.4. Загрузка маленькой и большой модели

Режим resident/demand задаётся профилем сервера. При demand диспетчер учитывает стоимость загрузки и память, может группировать bulk-этапы по модели, но не оставляет default без продвижения. После переключения выполняется health check.

Решение, сколько моделей помещается одновременно, определяется измерением VRAM. Имена «маленькая» и «большая» не заменяют реальные ресурсные параметры.

### 13.5. Будущая многопользовательская работа

В интерфейсе планировщика с первого дня есть owner_user_id и workspace_id. Позднее добавляются per-user admission limits, weighted round-robin и отдельные квоты без изменения task API. Для первой персональной версии не требуется сложное распределённое fair-share.

### 13.6. Периодические задачи

arq cron запускает:
- outbox dispatcher;
- task/confirmation reconciler;
- expiry reminder planner и delivery;
- lease watchdog;
- media orphan GC и archive purge;
- quota recheck;
- export expiry cleanup;
- backup status checks и метрики.

Планировщик идемпотентен. Несколько API-процессов не создают независимые копии cron. Лидерство или уникальный scheduled occurrence предотвращает дубли; пропущенное окно подбирается по durable next_run_at/occurrences после рестарта.

## 14. Поиск, дубли и согласованность индекса

### 14.1. Слои поиска

1. Exact lookup по UUID, штрихкоду, нормализованному серийному номеру и точной модели.
2. PostgreSQL FTS/trigram для названия, alias и аварийного текстового режима.
3. Dense embedding BGE-M3 для семантических запросов.
4. Локальный BM25 sparse encoder совместимой закреплённой версии; Qdrant объединяет dense/sparse через RRF.
5. Доменная фильтрация по категории, месту/поддереву, наличию остатка, сроку и lifecycle.
6. Формирование карточек кандидатов с ключевыми отличиями.

В первой реализации sparse encoder рекомендуется строить на локальном FastEmbed/Qdrant BM25 adapter с явно зафиксированной токенизацией и параметрами. Одни сырые TF без выбранной реализации BM25 не называются готовым BM25. OpenAI tokenizer можно проверить экспериментально, но он не является обязательным архитектурным условием.

Query/document используют одинаковые версии нормализации и sparse encoder. Источник IDF, коллекция и версия embedding задаются явно. После изменения алгоритма создаётся новая версия индекса, а не смешиваются несовместимые векторы. Схема dense+sparse+RRF описана в [документации Qdrant](https://qdrant.tech/documentation/search/text-search/hybrid-search/).

### 14.2. Поисковый документ

Отдельный point для карточки/экземпляра содержит entity_type, entity_id, workspace_id, entity_version, index_schema_version, privacy_policy, lifecycle, name, aliases, category, exact identifiers и разрешённые структурированные атрибуты.

Текст для embedding: название, подтверждённые признаки, aliases, теги и пользовательское описание. Неподтверждённое generated_description либо исключено, либо выделено в отдельный низкоприоритетный канал. Оно не подменяет истинные серийные номера/дозировки/сроки.

Для запросов по остаткам и срокам финальные данные читаются из PostgreSQL. Не требуется создавать отдельный вектор на каждое изменение количества. Фильтры права/tenant применяются до выдачи кандидатов и повторно проверяются при hydration из PostgreSQL.

### 14.3. Поведение результатов

GET search возвращает matched_by, explanation_short, item summary, варианты партий/мест, индексную ревизию и предупреждение о деградации при необходимости. Score не называется confidence правильного физического действия.

Примеры:
- «Что просрочено?» — детерминированный фильтр даты.
- «Где синие наушники?» — retrieval + места.
- «Переложи наушники» — retrieval + предложение с выбором кандидата, без изменения БД.
- «Есть ли таблетки 5 мг?» — dosage фильтр плюс поиск названия; 10 мг не объединяются с 5 мг.
- «Покажи то, что закончилось» — explicit availability=depleted.

Архив и deleted по умолчанию исключены фильтрами. Для истории available include_archived; deleted возвращаются только через соответствующий защищённый раздел до окончательной очистки. «Score=0» не заменяет фильтрацию.

### 14.4. Проверка дублей

Сравнение выполняется при подготовке receive_stock:
- точные идентификаторы;
- атрибуты варианта;
- семантические/визуальные кандидаты как подсказка.

Форма предлагает «Добавить к существующей карточке» или «Создать отдельную». Партия выбирается независимо от карточки. Точное совпадение названия не является уникальным DB-ограничением.

Перед применением повторно проверяются новые релевантные совпадения. Если появившийся объект создаёт существенный конфликт ранее показанного выбора, возвращается обновлённая форма. Если пользователь явно выбрал «отдельная вещь», похожесть сама по себе не запрещает создание.

### 14.5. Outbox

В транзакции изменения создаётся outbox_event с entity_id, entity_version, event_type, minimal payload. Dispatcher получает события через lease/SELECT FOR UPDATE SKIP LOCKED, не удерживая блокировку на время сети.

Индексатор загружает актуальное состояние, а не слепо применяет устаревший payload. События одной сущности сериализуются либо проверяют версию так, чтобы позднее старое событие не перезаписало новое. Reconciler сравнивает search_revision/indexed_revision и исправляет пропуски.

После исчерпания retry событие получает failed/dead-letter с причиной и доступно администратору для повторной постановки. Оно не удаляется как успешно обработанное. Мониторинг показывает возраст и число таких событий; исправленная зависимость позволяет выполнить повтор с тем же event_id.

Удаление создаёт tombstone/event и очищает point. При задержке индекса hydration всё равно не отдаёт удалённый объект. Перестройка индекса использует новую коллекцию и переключение alias после проверки.

### 14.6. Redis cache

Стартовое значение cache.enabled=false допускается. При включении используется один выбранный cache-aside с versioned namespace.

Ключи учитывают workspace, область видимости и поколения каталогов/локаций. После commit увеличивается поколение или удаляются точные ключи старого/нового места и предков. Позднее заполнение старого поколения не становится актуальным кэшем.

Ошибки кэша не должны откатывать подтверждённую операцию. Redis для кэша желательно изолировать от jobs по memory/eviction policy; очередь не должна выталкиваться политикой LRU ради списков.

## 15. Сроки годности и уведомления

### 15.1. Область первой версии

Уведомления относятся к истекающим и истёкшим срокам medicine, food и document. Напоминания о приёме отсутствуют. Произвольные таймеры вроде «напомни достать бутылку через час» также не входят в обязательную первую версию этого модуля.

Если исходная фраза содержит поддерживаемое перемещение и неподдерживаемый таймер, форма явно показывает, что таймер не создаётся, и предлагает подтвердить только перемещение. Неподдерживаемая часть запроса не исчезает незаметно.

### 15.2. Вычисление срока

- Известный день: сохраняется expiry_on с precision=day.
- Известен только месяц: сохраняется исходный YYYY-MM и precision=month; календарная граница определяется принятой настройкой month_expiry_policy и показывается в форме как нормализация, а не распознанный точный день.
- Пока политика интерпретации месяца не выбрана, UI предлагает один раз выбрать её или оставить срок без точного дня.
- Дата производства необязательна; система не требует её для обычного напоминания.
- Если задано открытие и срок после открытия, effective_expiry — наиболее ранняя применимая граница.
- Календарные месяцы после открытия вычисляются календарной арифметикой с явным правилом окончания месяца; они не всегда равны 30 суткам.
- Если срок неизвестен, уведомления по нему не создаются.

Для deadline «годен до дня включительно» момент перехода в expired — начало следующего локального дня в timezone правила. Изменение timezone не меняет исходную календарную дату. Неоднозначная интерпретация этикетки остаётся видимой пользователю.

### 15.3. Правила

reminder_rules содержит:
- owner_user_id/workspace_id, категории и область локаций;
- offsets_before_expiry в календарных днях;
- local_delivery_time, timezone, quiet_hours;
- send_expired, repeat_expired_interval, repeat_expired_max_count;
- group_mode(by_day/by_category/none);
- channels(in_app, optional push);
- include_archived=false по умолчанию;
- hide_sensitive_details_on_lock_screen;
- enabled и version.

Стартовые интервалы могут отличаться по категории и полностью редактируются. Механизм «доли полного срока жизни» не используется по умолчанию; его можно добавить позднее только при наличии достоверных обеих дат.

### 15.4. Создание occurrences

Planner рассчитывает конкретные occurrences на ограниченный горизонт. Уникальность: rule_id + subject_lot_id + expiry_generation + threshold_key + occurrence_time.

После изменения срока, открытия, правил или timezone:
1. Увеличить expiry_generation.
2. Отменить ещё не доставленные occurrences прежнего поколения.
3. Создать новые.
4. Не повторять уже доставленное эквивалентное уведомление без выбранного правила повторения.

Для tracked-lot без положительного остатка и без неизвестных остатков уведомление не создаётся. Для неизвестного остатка предупреждение допускается и помечается «наличие не подтверждено». Для документов/untracked срок действует независимо от numeric quantity, пока объект активен.

### 15.5. Доставка

Внутрисистемный inbox обязателен и создаётся идемпотентно. Push — отдельный адаптер с device tokens и permission state; он добавляется только при доступном канале, не заменяя inbox.

Статусы: planned, queued, sending, delivered, failed, cancelled, suppressed. Ответ push-провайдера «принято» не считается доказательством прочтения. Для внешней доставки не обещается физическое exactly-once: сохраняется dedupe key, возможные повторы учитываются интерфейсом и журналом.

После простоя planner подбирает просроченные occurrences. Несколько прошлых порогов объединяются в актуальное уведомление вместо потока старых предупреждений. Snooze, mark_read и dismiss меняют уведомление, а не исходный срок.

## 16. Настройки пользователя и администратора

### 16.1. Три разных уровня

1. Deployment configuration: пути, endpoints, секреты, порты, параметры процессов. Часть требует restart.
2. Admin runtime settings: лимиты, очереди, budgets, timeouts, media, retention, диагностика.
3. User preferences: отображение, предпочтительный маршрут в разрешённых пределах, напоминания, доступные сроки хранения.

### 16.4. Применение изменений

PATCH /admin/settings выполняет:
1. Проверку app_role=admin.
2. expected_revision, ключ идемпотентности и типизацию.
3. Проверку значений и зависимостей: heartbeat меньше lease; job hard timeout больше допускаемого вызова с запасом; context/output budget совместимы с runtime.
4. Dry-run результата и перечень требуемых restart.
5. Создание immutable settings_revision с автором и причиной.
6. Публикацию новой effective-конфигурации либо pending_restart.
7. Запись audit и подтверждение применённых/ожидающих ключей.

Если изменения требуют restart, совместный набор не объявляется полностью применённым до подтверждения всех необходимых компонентов. Для немедленных изменений и restart-набора допускаются отдельные ревизии. UI всегда различает desired и effective значения.

Каждая новая задача получает snapshot effective-настроек при создании. Изменение очередей может влиять на ещё не начатые задания согласно явно заданной apply_mode; модель/промпт/бюджеты задачи самопроизвольно не меняются. Аварийный запрет внешней передачи и отключение неисправного deployment действуют немедленно.

Rollback создаёт новую ревизию с прежними значениями. История не переписывается.

### 16.5. Административный UI-контракт

GET /admin/settings/schema возвращает группы, подписи, типы контролов, значения по умолчанию, единицы, ограничения и apply_mode. GET /admin/settings возвращает current value, effective value, source scope и revision.

Обязательные действия: проверить изменения, применить, сбросить к default выбранные ключи, посмотреть историю, откатить ревизию. Отдельно: health-check модели, пауза/возобновление очереди, повтор задачи, диагностический replay без записи в учёт, просмотр очередей и GPU slot.

Изменение системных параметров является явным действием администратора и не требует AI-HITL; подтверждение формы настроек достаточно. Административные команды не дают модели права менять параметры.

### 16.6. Диагностика

Администратор видит stage timeline, версии, выбранный маршрут, длительность ожидания и инференса, число попыток, нормализованный код ошибки, признаки усечения, размеры коллажа и статусы зависимостей.

Расширенный режим может показывать исходный/выходной payload внутри доверенного сервера в пределах выбранного retention. Он включается на ограниченную сессию с audit. Пароли, JWT, API-ключи и refresh tokens не показываются и не логируются даже в verbose.

Обычный пользователь получает понятное сообщение и request_id. Stack trace не возвращается ему в стандартном 500 response.

Тело POST /admin/settings/validate и последующего PATCH /admin/settings:

  "changes": [
    {"key": "timeout.local_inference_seconds", "value": 360},
    {"key": "timeout.worker_hard_seconds", "value": 480}

~~~

      "key": "timeout.local_inference_seconds",

## 17. Политики хранения, удаление и датасет

### 17.1. Жизненный цикл

depleted — вычисляемая доступность, не lifecycle и не основание автоматического hard delete. archived — явное скрытие с возможностью восстановления. deleted — запрос удаления с grace period. purged — удалённые данные и минимальный допустимый tombstone.

Частота GC и срок хранения — разные настройки. Ежедневный GC может удалять только объекты, которые уже соответствуют выбранному сроку.

### 17.2. Применение новой политики

Уменьшение retention не должно неожиданно удалять большой архив в момент сохранения настройки. Backend возвращает dry-run: число затронутых сущностей, объём, типы данных и дату ближайшей очистки. Для первого применения нового сокращающего правила администратор подтверждает policy impact.

Предварительно разрешённые регулярные чистки затем выполняются автоматически по этой политике. Дополнительное подтверждение каждого файла не требуется.

### 17.3. Purge

Purge job имеет устойчивый manifest целей, policy revision, actor/автоматическое основание, статусы по объектам и повторяемые шаги:
- отмена активных незавершённых задач/occurrences по удаляемой области;
- удаление bindings и проверка иных живых ссылок;
- очистка source/derived media;
- удаление search points и кэш-поколений;
- удаление/анонимизация подлежащих очистке полей БД и evidence;
- удаление копий из разрешённого dataset;
- сохранение минимального tombstone без удаляемого чувствительного содержимого.

После запроса удаления чтение блокируется доменным состоянием даже при отставании физической очистки. Резервные копии выходят из хранения по своей политике; восстановление применяет актуальный журнал удалений, чтобы не воскресить уже удалённые пользовательские объекты.

### 17.4. Датасет

datasets.enabled=false по умолчанию. При включении фиксируется, какие типы материалов и исправлений разрешены. Локальный trusted сервер допускает согласованное владельцем хранение, но не предполагает автоматическое обучение без настройки.

Запись примера содержит task/proposal revisions, входные references, predicted fields, confirmed fields и причины исправлений. Отмена ошибочного подтверждения помечает пример ненадёжным. Набор для оценки отделяется от будущего обучающего набора.

Дообучение — отдельная офлайн-процедура с versioned dataset, оценкой и возможностью отката модели. Изменение alias или подтверждение формы не запускает RLHF.

## 18. Полный REST API первой версии

### 18.1. Общие правила

Префикс /api/v1. Все методы, кроме login и ограниченных health probes, требуют аутентификации. workspace_id обязателен в scope запроса; в персональном клиенте он может подставляться из /me, но проверка остаётся серверной.

Пагинация списков: limit + cursor, стабильная сортировка по выбранному полю и id. Стандартный ответ: items, next_cursor, has_more. Максимальный limit берётся из настроек. UUID не заменяют проверку доступа.

Значимые изменения требуют версии объекта или предложения. Для POST-операций применяется Idempotency-Key. GET ничего не списывает, не перемещает и не подтверждает.

## 19. Polling и поведение клиента, обеспечиваемое бэкендом

Клиент начинает с poll_after_ms из ответа. Backend увеличивает интервал для долгого ожидания и сообщает изменения через status_version/ETag. If-None-Match может возвращать 304. Терминальный статус или waiting_for_review прекращает частый polling конкретной задачи.

Для десятков задач используется POST /tasks/status с id и известной status_version; сервер возвращает changed и unchanged ids. Максимальное число ids задаётся лимитом. Каждый id авторизуется отдельно.

В фоне частый polling приостанавливается; при возвращении клиент загружает review-inbox и список активных задач. Push при наличии является подсказкой открыть/обновить данные, а не единственным источником результата.

Подтверждение и его применение различаются визуально:
- «Подтверждено, сохраняется» после 202;
- «Сохранено» после confirmation.applied;
- «Данные изменились — проверьте обновление» после conflict.

Закрытие приложения не отменяет задачи. Черновики и подтверждения хранятся на сервере. Клиент может сохранять офлайн-черновик и загружать позже с тем же client_request_id; офлайн-изменение не изображается как уже применённое сервером.

На экране review после конфликта UI выделяет изменившиеся поля. Сохранённые пользовательские правки подставляются повторно там, где остаются допустимыми.

## 20. Транзакции, ограничения БД и восстановление

### 20.1. Минимальные ограничения

- UNIQUE(workspace_id, lot_id, location_id) для balances.
- UNIQUE(workspace_id, proposal_id, proposal_revision) для принятого confirmation.
- UNIQUE(workspace_id, operation_id) для применённой операции.
- UNIQUE(user_id, workspace_id, operation_scope, idempotency_key) для transport dedupe.
- UNIQUE(workspace_id, user_id) для membership.
- CHECK(quantity >= 0) при non-null.
- CHECK совместимости quantity_state/null.
- FK и workspace-consistency для item/lot/location/balance/task/proposal.
- Индексы tasks(status,next_attempt_at,priority,created_at), outbox(next_attempt_at,processed_at), lots(effective_expiry_on), entries(operation_id,ordinal), balances(lot_id), memberships(user_id).
- Частичные индексы активных карточек и ожидающих review.
- Ограничение individual-экземпляра обеспечивается сериализацией операций по lot и соответствующей проверкой; одного CHECK отдельного balance недостаточно.
- Циклы locations проверяются в транзакции с согласованной блокировкой затронутого дерева/workspace, чтобы два параллельных переноса не образовали цикл.

### 20.2. Образец алгоритма применения

~~~text
load confirmation
if already applied:
    return persisted result

begin transaction
    lock confirmation row
    lock proposal and source proposals if batch
    lock impacted item/lot/balance/location rows in deterministic order
    recheck versions, policy, identities, units and available quantities
    if conflict:
        rollback domain changes
        persist conflict and refreshed review in a separate short transaction
        return conflict
    create operation using the preallocated operation_id
    apply normalized actions in declared order
    write operation_entries and increase affected versions
    write outbox records for changed entities and reminder generations
    mark receipt/confirmation/proposal/task results
commit

publish completion hint through durable outbox
return persisted result
~~~

Передачи в MinIO, Qdrant, LiteLLM и push не входят в доменную транзакцию. Row locks и транзакции выбираются согласно [механизмам PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html); сетевой инференс не должен продлевать блокировки.

### 20.3. Матрица сбоев

| Момент сбоя | Ожидаемое поведение |
|---|---|
| Файл записан, media row не создана | Временный объект очищается, клиент повторяет загрузку |
| Task записана, Redis enqueue не выполнен | Outbox/reconciler повторно ставит задачу |
| ML ответил, worker упал до checkpoint | Допустим ограниченный повтор вызова; учёт ещё не менялся |
| Ответ старого worker пришёл после retry | Fencing отклоняет устаревший результат |
| Confirm принят, очередь недоступна | Confirmation сохранён; применение будет восстановлено |
| Изменение БД выполнено, HTTP ответ потерян | Повтор возвращает существующий operation result |
| Qdrant не обновился | Outbox повторяет; PostgreSQL остаётся актуальным |
| Push отправлен, delivery ack не записан | Возможен внешний повтор с dedupe key; in-app запись одна |
| Redis утрачен | Восстановить задания из PostgreSQL; кэш перестроить |
| Диск заполнен | Новые загрузки отклоняются заранее/понятно; существующий учёт не удаляется автоматически |
| Локальная модель недоступна | Задачи ждут или дают ручное продолжение; private не уходит в облако |
| Запрос cancel соревнуется с confirm | Один выигрывает блокировку; после принятого confirm cancel отвечает конфликтом |
| Настройки обновились во время задачи | Используется snapshot, кроме аварийных ограничений |

### 20.4. Резервное копирование

Обязателен backup PostgreSQL и согласованная политика объектов MinIO. Backup includes schema version, application version и список object references. Qdrant можно восстанавливать переиндексацией; его backup сокращает время, но не заменяет PostgreSQL.

Секреты и ключи восстановления хранятся отдельно от общедоступных файлов приложения. Резервная копия на том же единственном диске не считается защитой от потери диска. Конкретные RPO/RTO и место копий выбирает владелец в deployment-профиле.

Не реже выбранного интервала выполняется пробное восстановление в отдельную тестовую область: проверить counts, связи, несколько медиа, очередь незавершённых задач и последующую переиндексацию. До снятия maintenance после restore применяются актуальные tombstones удаления.

## 21. Аутентификация и защита границ

### 21.1. Личный запуск

Bootstrap CLI создаёт admin, workspace, membership и начальную settings revision. Пароль не записывается в репозиторий или образ. Открытая регистрация не включается автоматически после deployment.

Пароли хешируются поддерживаемой реализацией Argon2id с параметрами профиля сервера. JWT проверяет подпись, разрешённый алгоритм, issuer, audience, expiration и состояние пользователя/session. Длительность access и refresh — настраиваемые deployment-параметры.

Refresh token ротируется; хранится его hash и family. Повтор отозванного токена обрабатывается как компрометация session family. Logout-all увеличивает auth_version/отзывает sessions. Восстановление доступа владельца возможно через защищённый серверный CLI.

### 21.2. Клиенты

Для web refresh хранится в HttpOnly Secure cookie с согласованной SameSite/CSRF политикой; разрешённые CORS origins задаются явно. Для native refresh возвращается по защищённому протоколу и должен сохраняться клиентом в защищённом хранилище устройства. Профиль клиента определяется договорённым auth-контрактом, а не произвольным обходом CSRF.

Access tokens и API-ключи не входят в query string, ссылки на медиа или логируемые payload.

### 21.3. Авторизация

Обязательна проверка workspace membership на всех ресурсах, включая task, proposal, confirmation, export и download. Фильтр Qdrant не считается единственной защитой. Перед изменением повторно проверяются права и существование источника/назначения.

Админские настройки требуют app_role=admin. Role не доверяется клиентскому JSON. Если роль изменилась, устаревшая session не сохраняет административный доступ до бесконечного истечения JWT.

### 21.4. Входные данные

- Ограничения bytes, размеров декодированных изображений, длительности, числа действий.
- Типизированные allowed fields для PATCH и command payload.
- Parameterized SQL; имена таблиц/полей не приходят из LLM.
- HTML/текст модели отображаются как текст, без исполнения.
- URL, QR-коды и ссылки внутри фотографий не скачиваются автоматически сервером.
- Upload endpoint не принимает произвольные filesystem paths.
- Таймауты, ограничение памяти и изоляция процессов декодирования.
- Секреты хранятся в secret store/environment вне экспортов и UI; endpoint refs не раскрывают credentials.

### 21.5. Сетевые права

Только gateway/разрешённый cloud worker имеет необходимый внешний доступ к AI endpoints. Локальный inference и обработчики приватных медиа не получают произвольного внешнего egress, если это технически возможно в выбранном deployment.

Наблюдаемость, error tracking и аналитика по умолчанию остаются в доверенном контуре. Подключение внешней телеметрии не должно начать отправлять private payload.

## 22. Экспорт, наблюдаемость и эксплуатационные требования

### 22.1. Экспорт

Экспортируется подтверждённое состояние с schema_version, exported_at, timezone и версиями справочников:
- JSON: entities, связи, остатки, количество/точность, даты, история по выбранной опции.
- CSV: отдельные таблицы items, lots, balances, locations; unknown не превращается в 0.
- ZIP: JSON/CSV плюс связанные медиа и manifest checksums при include_media=true.

Экспорт не содержит секретов, паролей, refresh tokens и provider credentials. Приватные данные владельца включаются только в его авторизованную область и сохраняются на доверенном сервере. Готовый объект имеет TTL и доступен по временной авторизованной ссылке.

Для человекочитаемого CSV значения, похожие на формулы таблиц, безопасно экранируются; машинный JSON сохраняет исходный текст. Экспорт создаётся фоново и не держит одну долгую блокирующую транзакцию; согласованность снимка определяется snapshot boundary/export_revision.

### 22.2. Структурированные логи

request_id, task_id, attempt_id, proposal_id/revision, confirmation_id, operation_id и config_revision связывают путь запроса. В обычных логах сохраняются технические поля и нормализованный error_code. Не требуется логировать содержимое документов ради наблюдения за latency.

Audit параметров и операции учёта имеют отдельное назначение и retention. Успешная очистка диагностических payload не должна уничтожать подтверждённые карточки.

### 22.3. Метрики

| Группа | Метрики |
|---|---|
| HTTP | p50/p95 latency по типу endpoint, error rate, inflight |
| Очереди | ready/running/review counts, возраст старейшей задачи, wait duration |
| ML | wall time, model load time, attempts, invalid JSON, external fallback reasons |
| GPU | доступность, занятость, VRAM при наличии метрик runtime |
| Review | доля one-click confirm, число изменённых полей, типы блокеров, review duration |
| Корректность | rejected stale confirms, duplicate requests, prevented negative stock, reversals |
| Стоимость | внешние вызовы, известная стоимость, оценочное GPU-время на подтверждённую операцию |
| Согласованность | outbox lag, index lag, размер dead-letter, недоставленные notifications |
| Хранение | bytes source/derived, рост, GC backlog, backup age |
| Приватность | число запрещённых egress попыток, policy reasons, неизвестные классификации |

Время нажатий/правок может передаваться минимальными клиентскими событиями. Backend не выдумывает активное время пользователя из длительности открытой задачи. Metrics labels не содержат произвольные имена предметов и приватные тексты.

### 22.4. Состояние сервиса

/health/ready зависит от возможности безопасно обслуживать базовые операции с PostgreSQL и конфигурацией. Недоступность ML не делает чтение каталога недоступным. Подробный health показывает degraded capabilities: upload, local_ml, cloud_ml, search_semantic, reminders_delivery.

Новые задачи можно принимать при кратковременной недоступности Redis, если durable приём и admission limits работают. При переполнении диска/предела backlog API даёт понятный отказ и не обещает бесконечную очередь.

### 22.5. Измеряемые параметры качества

До первого запуска фиксируются тестовый размер каталога, число медиа, размер пакетной загрузки, модель/квантование и оборудование. На них измеряются поиск, обычный CRUD, время создания формы, обработка очереди и восстановление.

100 секунд локального инференса не являются договорным SLA. Аналогично 5–10 секунд активного ввода и любые проценты локального успеха являются проверяемыми продуктовыми целями, которые уточняются на реальной установке.

Надёжность транзакций и отсутствие изменений до HITL — жёсткие критерии независимо от скорости.

### 23.3. Схемы и совместимость

- HTTP API описывается генерируемым OpenAPI.
- review.v1, extraction.v1, collage.v1 и export.v1 имеют JSON Schema и набор contract fixtures.
- Добавление необязательного поля допустимо в пределах совместимого minor изменения.
- Изменение смысла существующего поля или типа control требует новой версии.
- Клиент сообщает поддерживаемые review schema/control versions.
- Для неизвестного клиенту control backend предлагает совместимый шаблон либо явную ошибку обновления; не возвращает пустую необъяснимую форму.
- Переход между версиями модели не меняет публичный API без отдельного изменения schema.
- Миграции данных сопровождаются backfill/rollback планом; production не запускается через create_all вместо Alembic.

### 23.4. Промпты

Системная часть содержит роль извлекателя данных, правила unknown, допустимые intents, запрет исполнения инструкций из изображений и требование выходной схемы. Отдельно передаются:
- текущая задача;
- пользовательский текст/транскрипт;
- один image/collage;
- manifest областей;
- минимальный набор кандидатов с отличиями;
- справочники разрешённых категорий/единиц;
- уже подтверждённые значения, которые нельзя молча перезаписать.

Промпт не обещает, что модель сама обеспечивает приватность или транзакционность. Эти правила реализованы сервисами.

## 24. Порядок реализации

### Этап 0. Репозиторий и окружение

Зафиксировать версии, lock-файл, конфиги окружений, Compose-сервисы, health checks, миграции, bootstrap admin и пример безопасной конфигурации без секретов.

Реализовать users/workspace, locations, items/lots/balances, units, manual-confirm, journal, idempotency, optimistic versions, partial move, archive/restore и reverse-preview.

Результат: пользователь может вручную вести корректный каталог; конкурентные и повторные запросы не портят остатки.

### Этап 2. Proposal/HITL contract

Реализовать формы по операциям/категориям, typed changes, previews, confirm receipt, CPU apply, review-inbox, batch-preview, конфликты и восстановление правок. Использовать детерминированный fake extractor.

Результат: фронтенд может строить user-friendly формы и проходить сценарий одной кнопки без подключения реального ML.

### Этап 3. Durable tasks и outbox

Реализовать state machine, dispatch, retry, lease/fencing, cancellation, polling, reconciler, high_priority CPU queue. Проверить остановки между транзакциями.

Результат: задачи и подтверждения переживают restart API/worker и потерю Redis.

### Этап 4. Медиа и коллажи

Upload, source/derived assets, нормализация, ограничение пикселей, thumbnails, deterministic collage manifest, crops и cleanup. Контракт «один image input на вызов» проверяется тестом adapter boundary.

Результат: 1/2/3 снимка одной вещи превращаются в воспроизводимый локальный вход; пользователь может проверить источник даты.

### Этап 5. Локальная Gemma и ASR

Capabilities smoke test, первичная privacy/ASR стадия, локальная VLM, схемы JSON, repair budget, field provenance и частично заполненные формы. Реальный медленный inference подключается через очередь.

Результат: фото/голос дают форму; GPU освобождается до review; подтверждённые данные не меняются до клика.

### Этап 6. Поиск и кандидаты

PostgreSQL exact/text, BGE-M3, BM25 adapter, Qdrant, фильтры и outbox indexer. Протестировать одинаковые названия, дозировки, aliases и pending indexing.

Результат: пользователь выбирает подходящие существующие карточки без перепечатывания названия.

### Этап 7. Внешние модели

LiteLLM gateway, allowlisted deployments, policy gate, бюджет попыток/стоимости, cooldown, proxy transport и provider error mapping. Включение только после успешных policy tests.

Результат: cloud_allowed задачи получают управляемый fallback; local_only не покидает контур.

### Этап 8. Сроки и inbox

Expiry precision, opening rules, planner, occurrences, генерации, доставка in-app, quiet hours, grouping и catch-up. Push добавляется при доступном выбранном канале.

Результат: корректные уведомления по срокам; никаких графиков приёма.

### Этап 9. Admin settings и эксплуатация

Registry/schema UI, snapshots, validation/dry-run, desired/effective state, history/rollback, queue pause, trace, replay, GC, exports и backup runbook.

Результат: владелец калибрует параметры без ручных правок БД и понимает, какие значения использовала конкретная задача.

### Этап 10. Приёмка на личном наборе

Загрузить согласованный набор вещей и медиа; пройти сценарии ниже; измерить очереди, one-click review и качество отдельных полей. Сохранить baseline profile и список калибруемых параметров.

| T-76 | CSV содержит имя, начинающееся с = | Человекочитаемый экспорт не исполняет его как формулу |
| T-77 | Аптечка добавлена и расходуется | Нет сущностей/уведомлений графика приёма |
| T-78 | Истёк срок хранения исходного аудио | Подтверждённый учёт и полезная история сохраняются |
| T-79 | Unknown остаток перемещается к известному того же lot | Явная форма выбора; известное количество не теряется |
| T-80 | Технически упало применение принятого confirm | Retry использует прежние confirmation_id/operation_id, без повторного ML-намерения |

### 25.7. Проверка реальных моделей

Сформировать небольшой набор собственных, разрешённых к использованию примеров:
- упаковка лекарства: название, форма, дозировка, остаток, срок;
- несколько партий одного товара;
- документ с датой окончания;
- вещь без надписи;
- три ракурса одного предмета;
- сложный свет и мелкая этикетка;
- короткие голосовые команды и отрицания;
- неоднозначные похожие предметы;
- чувствительные сведения в небольшой области кадра.

Разметка содержит истинные значения и допустимые unknown. Измеряется качество каждого поля, доля одношагового подтверждения, число дополнительных проходов и суммарное время. Не требуется достигать заранее выдуманных 80% для приёмки архитектуры.

## 26. Definition of Done первой версии

Релиз считается готовым к личной эксплуатации, когда:

- Выполнены D-01…D-13 и INV-01…INV-14.
- Ручной учёт полностью работает без ML.
- Фото/аудио/текст создают сохранённую предзаполненную форму.
- Принятие формы и применение операции различаются, восстанавливаются после сбоев и идемпотентны.
- Вызов локальной VLM с несколькими image inputs технически невозможен через штатный адаптер.
- Ни один tested local_only путь не обращается к внешнему AI.
- Review-inbox переживает закрытие клиента и перезапуск сервера.
- Остатки, партии и частичные перемещения соответствуют журналу.
- Поиск не определяет истинность данных и не обходит права.
- Напоминания действуют только в установленной области сроков.
- Администратор видит/меняет параметры, знает apply_mode и может откатить настройку.
- Настроены резервные копии и выполнено успешное пробное восстановление.
- OpenAPI, JSON schemas, миграции, runbooks, профиль настроек и тесты поставляются с кодом.
- Все применимые T-01…T-80 проходят; реальные ML-ошибки превращаются в безопасную форму/unknown и не нарушают инварианты.

## 27. Комплект поставки и запуск

Разработчик передаёт:
1. Репозиторий бэкенда с lock-файлами и миграциями.
2. Compose/deployment-конфигурацию с отдельными API, CPU, ML dispatcher, scheduler и зависимостями.
3. Пример environment без секретов и bootstrap CLI.
4. OpenAPI и versioned JSON Schema для публичных форм/команд.
5. Справочники и стартовый personal-профиль.
6. Автоматические тесты и синтетические fixtures без чужих приватных данных.
7. Runbook запуска, обновления, backup/restore, восстановления очереди, reindex и диагностики модели.
8. Список реальных model deployments и результатов capabilities проверки.
9. Описание включённых внешних соединений и фактической границы доверенного контура.
10. Результат личной приёмки и измеренные значения, которыми заменяются стартовые догадки.

Порядок запуска: подготовить секреты/диск → поднять зависимости → миграции → bootstrap admin → проверить локальный model adapter → API/CPU/scheduler → выполнить ручную операцию → пробное фото → review/confirm → проверка восстановления → при необходимости включить внешний маршрут.

Отдельная live проверка внешних моделей проводится на несекретном fixture и не требуется для local-only эксплуатации.

## 30. Правило сопровождения спецификации

Перед изменением публичного контракта, доменного инварианта или границы доверия создаётся короткий ADR: причина, выбранное решение, альтернативы, миграция данных и влияние на тесты.

Настройка порога, веса очереди или таймаута в предусмотренных пределах не требует переписывать архитектуру. Она фиксируется новой settings revision и проверяется на личном наборе. Значения, качество модели и скорость могут меняться; подтверждённый учёт, история и понятная форма остаются устойчивыми.
